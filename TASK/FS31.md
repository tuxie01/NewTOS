# FS31 — Loeschen auf einem Laufwerk trifft offene Dateien auf einem anderen

Status: **UMGESETZT — Tester offen** (2026-11-06) · Prioritaet: **P1** · Typ: Belegter Defekt, Datenverlust — aus [HW08](HW08.md), Pi-Lauf

## Befund

`tos-api/src/bdos/fs/file.rs:670@ixdel` erkennt die offenen Dateien des zu loeschenden Eintrags mit `o.dir_start == dir_start && o.dir_slot == slot`, **ohne Laufwerk**. Zwei Stammverzeichnisse haben beide `dir_start` 0: Das Loeschen eines Eintrags auf D: trifft eine offene Datei auf C:, die zufaellig dieselbe Slot-Nummer hat.

Wirkung bei einem Treffer, gelesen: Die fremde Datei wird als geloescht markiert (`deleted`, `listed = false`, `dirty = false`), ihre ausstehende Laenge ist verloren, `Fwrite` liefert `EACCDN`, `Fclose` liefert `EINTRN`. Vorher kann `ixclose` sie schliessen oder das Loeschen faelschlich mit `EACCDN` ablehnen.

Beleg: FSWBENCH auf der echten Pi, offenes `C:\FSWBENCH.LOG`, Loeschvorgaenge nur auf D:, keine Treiberfehler: `log last Fwrite=-36 Fclose=-65` (`measurements/measurement-2026-11-06-hw08-pi2/RUNINFO.TXT`). Der Mechanismus ist aus dem Code gelesen; dass genau er diese beiden Kodes erzeugte, belegt erst der rote Test.

EmuTOS: `d_files` haengt am Verzeichnisknoten und der gehoert zu einem Laufwerk (`bdos/fs.h:219`, `:224`), dort kann das nicht passieren. `move_ofds` in derselben Datei vergleicht das Laufwerk (`tos-api/src/bdos/fs/file.rs:1089@move_ofds`). Herkunft: `f5efac77` (PROC04 Punkt 5).

## Auftrag

Roter Test zuerst (zwei Volumes, gleiche Slot-Nummer), am Orakel gegenmessen (Fall auf zwei Laufwerken), Fix minimal, alle Stellen derselben Art im BDOS mitpruefen (auch die Faelle, in denen `dir_start` und `dir_slot` als Schluessel allein stehen). Lokalisieren nach CLAUDE.md "Testing", Retest-Set ins Ticket. Andere Kartenprogramme mit offener Datei auf einem Laufwerk und Loeschen auf einem anderen nennen, soweit in den Quellen sichtbar.

Abnahme: Hosttest rot auf der Basis, gruen danach; Orakel gleich; `Fdelete` einer offenen Datei auf demselben Laufwerk wie bisher (PROC04, `docs/COMPATIBILITY.md`); FSWBENCH-Protokoll auf C: vollstaendig.

[Gemeinsame Regeln](README.md) gelten.

## Umsetzung (2026-11-06)

**Beleg:** Der Mechanismus stimmt, der Hosttest wird rot mit genau den beiden Kodes des Pi-Laufs (-36, -65). `measurements/measurement-2026-11-06-fs31/RUNINFO.TXT`.

**Fix:** `ixdel` vergleicht zusaetzlich das Laufwerk des OFD (`tos-api/src/bdos/fs/file.rs:672@ixdel`). Spec: `docs/api/gemdos/file/41-fdelete.md`, FS31.

**Orakel:** Hatari faehrt den Fall, ein Abbild mit drei Partitionen, gleiche Kartenbytes auf beiden Seiten, gleiche Nummern im Log belegt. EmuTOS trifft das andere Laufwerk nicht. NewTOS rot in den Faellen A B C D E F G J, nach dem Fix das Log bytegleich. Sonde `tosdump/probes/xdprobe.c`, tosdiff-Fall: [FS32](FS32.md).

**Gepruefte Stellen derselben Art:**

| Stelle | Schluessel | Ergebnis |
|---|---|---|

| `flush_ofd`, `fdatime`, `ixclose` | nutzen `ofd.s.vol` | richtig, Test `Fdatime` |
| `free_drive_files` (`offree`) | `vol.drive()` | richtig, Test Medienwechsel auf D: |
| `Fsnext`-Zustand im DTA | Laufwerk in Byte 8 | richtig, Test, Orakel O |
| `curdir`: `dirtbl[]`, `live`, `find`, `free_drive`, `reclaim`, `inherit`, `release` | Laufwerk + Pfad | richtig, Test, Orakel P |
| `path::current_dir_cluster`, `dsetpath`, `dgetpath` | Laufwerk des Pfads | richtig, Test, Orakel P |

**Retest-Set** (`cargo xtask deps ixdel --up`, 113 Funktionen, `bdos` vollstaendig, 0 unmapped): `xunlink`/`ixunlink` → `fdelete`; `xcreat`/`ixcreat` → `fcreate`; `xrmdir` → `ddelete`; `xrename` → `frename`; `xmkdir` → `dcreate` (hat in NewTOS keinen `ixdel`-Pfad); `sc_clear` → `tos-api/src/aes/shell.rs@scrp_clear`; darueber `osif`/`enter` und die AES-Pfade `crysbind`, `sh_main`. Tests: `fs31_two_drives`, `proc04_fdelete_open`, `fs18_frename`, `fs18_frename_lfn`, `fs20_media_change`, `fs21_close_archive`. Schicht `desk` und `include` sind in `mapping.tsv` nicht abgebildet, Desktop deshalb von Hand unten.

**Betroffene Programme, aus den Quellen** (Bedingung jeweils: gleiche Slot-Nummer und gleiches Verzeichnis-Startcluster auf beiden Laufwerken, also Glueck und Fuellstand):

- **NEWDESK**, Kopieren/Verschieben auf ein anderes Laufwerk ueber eine bestehende Datei (`programs/desktop/src/dir.rs:994@d_dofcopy`): Quelle offen, `Fcreate` ueber das Ziel, die Quelle liest 0 Byte, kein Fehler, das Ziel bleibt leer. Beim Verschieben loescht `programs/desktop/src/dir.rs:1144@d_dofdel` danach die Quelle. **Beide Inhalte weg.**
- **TeraDesk**, derselbe Weg (`sdk/apps/teradesk/copy.c:832`, `:839`, Loeschen der Quelle `:1822`): `x_close(fh1)` wertet das `EINTRN` nicht aus.
- **FSWBENCH**: der Anlass. **HypView**, Loeschen von `SCRAP.*` (`sdk/apps/hypview/block.c:186`), und **`scrp_clear`** (`tos-api/src/aes/shell.rs`): treffen eine offene Datei auf einem anderen Laufwerk. Offen ist dort nur, was das Programm in dem Moment offen haelt.
- Ein Kind, das auf einem Laufwerk loescht, waehrend der Elternprozess auf einem anderen eine Datei offen hat, bekam `EACCDN` (Orakel-Fall G). QED und HighWire loeschen, in den gelesenen Stellen (`sdk/apps/qed/src/file.c:353`, `:371`, `sdk/apps/qed/src/options.c:1710`, `sdk/apps/highwire/src/cache.c:937`), Dateien neben der bearbeiteten; eine offene Datei auf einem anderen Laufwerk ist dort nicht sichtbar.

**Offen fuer die Abnahme:** FSWBENCH-Protokoll auf C: auf der echten Pi. In QEMU rot `log last Fwrite=-36 Fclose=-65`, gruen `Fwrite=61 Fclose=0`, Protokoll 4215 Byte vollstaendig. Die Quittung kommt mit der Abnahme.
