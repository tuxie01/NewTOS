`tos-api/src/aes/appl.rs` `reported_pid` liefert fuer jeden Client
`AP_CHAIN_PID` (0), und `identity_of(0)` ist immer der Aufrufer. Der
Doc-Kommentar sagt noch „Desk accessories (pid 2+, `D.g_acc[]`) do not exist
here“ — Accessories laufen aber inzwischen (SYSACC, auf der Pi abgenommen).
In EmuTOS bekommen Accessories pid 2… (`totpds = num_accs + 2`,
`aes/geminit.c:819`). Folge: `appl_write` zwischen Programm und Accessory ist
nicht moeglich; `appl_find` duerfte ebenfalls betroffen sein.

Auftrag: EmuTOS' Vergabe der ap_id fuer Accessories und `appl_find`/
`appl_write`-Adressierung lesen, gegenueberstellen, angleichen; Test mit
Accessory ↔ Programm-Nachricht. Erst nach A112 (gleiche Weckwege).
Quelle: `docs/analysis/a112-evnt-multi-mesag-2026-10-17.md`, Nebenbeobachtung.

[Gemeinsame Regeln](README.md) gelten.

## Ergebnis (2026-10-17, Auditor) — bestaetigt

Belege `measurements/measurement-2026-10-17-a113-a114/RUNINFO.TXT`
(`serial/idprobe1.log`).

| | NewTOS (Lauf) | EmuTOS (Quelle) |
|---|---|---|
| ap_id ACCX / ACCY / Programm | 0 / 0 / 0 | 2 / 3 / 0 |
| `appl_find("ACCX")`, `("ACCY")` | 0, 0 | 2, 3 |
| Programm `appl_write(find(ACCX))` | landet in der **eigenen** Queue | beim Accessory |
| `appl_write(2)`, `(3)` | 0, nichts zugestellt | zugestellt |
| `msg[1]` im WM_REDRAW an ein Accessory | 0 | 2 bzw. 3 |

EmuTOS: `totpds = num_accs + 2` (`geminit.c:819`), pid 0 = Kette (Desktop,
Programm, Pexec-Kinder), 1 = SCRENMGR, Accessories 2.. in Ladereihenfolge
(`geminit.c:252-255,851-877`, `gempd.c:60-70`); `appl_find`/`appl_write`
ueber `fpdnm` (`gemaplib.c:95-107`, `gemsuper.c:101-105`); `msg[1]` =
Absender-pid (`gemwmlib.c:851-862`); `WF_OWNER` (`gemwmlib.c:1580`).
NewTOS: `reported_pid` immer 0, `identity_of(0)` = Aufrufer
(`tos-api/src/aes/appl.rs:214-238`); betroffen `appl_init`, `appl_find`,
`appl_write`, `appl_read`, `mn_cleanup`, `send_redraw`, `WF_OWNER`,
`pid_of_slot`.

Wirkung (Quelle): AV-Protokoll zwischen TeraDesk und Accessories
(`va.c:789,798,835,1002,1163-1169`), QED/HighWire → ST-Guide o. ae.
SYSACC nicht betroffen.

Spec: `docs/api/aes/application.md` EmuTOS-Teil richtig (Z. 47-51,
825-831); falsch/veraltet NewTOS-Vertrag (b) (Z. 106-147), Z. 575-585 samt
A75-Begruendung, Z. 962-968, `appl_exit` Schritt 2 (Z. 652, `mn_cleanup`).

Fix-Vorschlag: `reported_pid` = 2 + feste Position in `ACC_PDS`, sonst 0;
`identity_of(0)` = aktuelles Kettenmitglied (innerstes lebendes
Nicht-Accessory, nicht der Aufrufer), 1 = SCRENMGR, 2+n = `ACC_PDS[n]`.
Spec und Kommentare mitziehen. Test: idprobe gruen (2/3/0, Austausch
0x4000/0x4001 mit `m1` = 2/3, `WF_OWNER`, `appl_write(4)` = 0), Hosttests,
Pi mit TeraDesk + AV-Accessory.
