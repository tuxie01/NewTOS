# HW09 — SD card in High-Speed mode (50 MHz) for faster image loading

Status: OPEN (2026-11-12) | Priority: P2

Type: developer (EMMC2 driver), then a real-Pi run with the owner. Owner 2026-11-12: "ok dann SD High Speed, weil
gerade wenn man zView nimmt und Bilder öffnen will das dauer einfach ganz schön lange" (ok, then SD High Speed,
because especially when you take zView and want to open pictures it just takes quite a long time).

## Facts

- The EMMC2 driver runs the card at default speed: `set_clock(25_000_000)` after identification
  (`kernel/src/drivers/bcm2711/emmc.rs:1329@set_clock`), 4-bit bus (`ACMD6`), PIO, polled. Ceiling 25 MHz x 4 bit
  = 12.5 MB/s.
- Measured on the real Pi: up to 9447 KB/s for one large call, 5115 KB/s for `Rwabs` with 128 sectors per call
  (`measurements/measurement-2026-11-06-hw08-pi2/RUNINFO.TXT`). [FS08](FS08.md) already removed the software
  bottlenecks of image loading (2026-10-22: 10 MB `Fread` 14479 -> 875 ms); what remains is close to the bus limit.
- High-Speed mode (50 MHz, 25 MB/s ceiling) is switched by `CMD6 SWITCH_FUNC` (SD Physical Layer Simplified Spec
  9.10, `references/sd-spec/Part1PhysicalLayerSimplifiedSpecificationVer9.10Fin_20231201.pdf`, §4.3.10) and, on the
  host side, the High Speed Enable bit of Host Control 1 plus the clock divider (SD Host Controller Simplified Spec
  4.20, `references/sd-spec/PartA2_SD_Host_Controller_Simplified_Specification_Ver4.20.pdf`). Section numbers are
  checked by the developer when the spec entry is written; they are not settled here.
- Not known yet: how much of zView's opening time is reading and how much is decoding. If decoding dominates, this
  ticket helps little; step 1 answers that before any driver change.
- DMA for the SD card is a separate, later step: after [SND05](SND05.md) provides the DMA driver with the cache
  maintenance measured in `measurements/measurement-2026-11-12-snd03-pi/RUNINFO.TXT` (H3). Not part of this ticket.

## Work

1. Baseline on the real Pi: time to open the owner's pictures in zView (`C:\Bilder\`), split into file read and the
   rest, plus the read throughput of a large file at 25 MHz. Measured, recorded as a run.
2. Hardware note: the CMD6 query/switch sequence, the host-side High Speed Enable and clock divider, what the card's
   CMD6 status reports, the fallback when the card or the host refuses (stay at 25 MHz, no error to the caller). Track
   B sources only (CLAUDE.md rule 6); the EMMC2 base clock as the driver already obtains it.
3. Implementation in `kernel/src/drivers/bcm2711/emmc.rs`: query (CMD6 mode 0), switch (mode 1) only if the card
   supports High Speed, then host High Speed Enable and 50 MHz; verify with a read. Host tests where the logic allows
   (status decoding, divider computation).
4. Real-Pi run with the owner: the same measurements as step 1 at 50 MHz, plus a file copy and compare (data
   integrity), on the owner's card.

## Acceptance

- Step 1 and step 4 measured on the real Pi, recorded as runs; read throughput above the 25 MHz ceiling, or the run
  shows why not.
- A card or host without High Speed stays at 25 MHz and works as before (QEMU raspi4b boot and file tests unchanged).
- Copied files compare equal; `cargo xtask test` green; warnings delta 0; spec/hardware note doc-check clean.
