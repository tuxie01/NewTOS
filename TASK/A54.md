## Der Befund (Fälle 331, 332, 439)

EmuTOS (`aes/gemwmlib.c:1563-1565`) reicht durch zu `gsx_mret`
(`aes/gemgsxif.c:96-129`) und liefert Adresse **und** Länge des
Menü-/Alarmpuffers. Gemessen: Adresse `0x01000218`, Länge `40960`.

NewTOS (`tos-api/src/aes/window.rs:2672-2679`):

```rust
if field == WF_SCREEN {
    for i in 1..=4 { pb.set_intout(i, 0); }
    pb.set_ret(1);
    return;
}
```

Vier Nullwörter — **und `ret = 1`**, also Erfolg behauptet.

## Warum das schwerer wiegt als eine Nulladresse

Ein Aufrufer kann nicht unterscheiden zwischen „es gibt keinen Puffer" und „hier
ist einer, er liegt bei 0". Mit `ret = 0` wäre es eine ehrliche Absage; mit
`ret = 1` ist es eine falsche Auskunft. Regel-2-Nähe.

## Der Kommentar im Code ist zu prüfen, nicht zu übernehmen

Dort steht „Assessed deliberate deviation (AUD-P5-012)". Der Auditor
**widerspricht**: eine Begründung ist keine Unbeobachtbarkeit, und der Wert ist
über die dokumentierte API sehr wohl beobachtbar. Wer das Ticket bearbeitet,
prüft AUD-P5-012 nach und stellt entweder den Code richtig oder die Bewertung —
aber nicht keines von beidem.

## Abnahme

Ein Aufrufer bekommt Adresse und Länge, oder eine ehrliche Absage. Gegenmessung
mit `aes-r4-subfunctions.tsv` gegen `EMUTOS14-AES-r4.BIN` — ohne Hardware
fahrbar.

## Arbeitsregel

[Gemeinsame Regeln](README.md) gelten. Bei belegter Abweichung von EmuTOS ist
die Vorgabe **angleichen**, nicht rechtfertigen. Test vor Fix.

`docs/analysis/aes-audit/p5-window-graf.md` als Bewertung zurückgenommen und
