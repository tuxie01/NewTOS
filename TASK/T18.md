## Die Stellen

**1. USB: VL805 an fester Adresse `0xFE9C0000`** — seit dem Nachtrag zu
ADR-015 (2026-10-26, `docs/MEMORY.md`) falsch: der VL805 ist ein
PCIe-Endpunkt, der Kernel zaehlt ihn auf und legt seine xHCI-BAR ins
Outbound-Fenster bei CPU `0x6_0000_0000` (`kernel/src/drivers/usb/pcie_rpi4.rs:1-21`).
`0xFE9C0000` kommt im Code sonst nirgends vor.
- `kernel/src/drivers/usb/mod.rs:15-18` („D7 real Pi-4 (VL805 firmware @
  `0xFE9C0000`)“)
- `kernel/src/drivers/usb/mod.rs:89-90` („the real Pi-4 path (VL805 firmware
  + `0xFE9C0000`) is PHASE-16 D7“)
- dazu beim Pruefen getroffen: `kernel/src/drivers/usb/mod.rs:27-28`
  („the real Pi-4 (D7) = fixed MMIO + VL805 firmware“) und
  `kernel/src/drivers/usb/mod.rs:22-23` („Scaffold … the concrete modules
  (xhci, pcie, core, hub, hid) land per PHASE-16 D1..D7“ — D7 ist abgenommen,
  `core`/`hub` gibt es nicht als Module). Ob das `#![allow(dead_code)]` in
  `:24` danach noch gebraucht wird, prueft der Developer; entfernen nur, wenn
  der Bau ohne neue Warnung bleibt.

**2. AESGLOBAL: „user VA below 32 MiB (`USER_TPA_MAX_VA`)“** — seit
ARCH03/ADR-028 (VA = PA) ueberholt; die Konstante gibt es in `tos-api/src`
nicht mehr. Heutige Grenze der Benutzertabellen: `USER_VA_LIMIT` = 4 GiB
(`tos-api/src/bdos/process/mmu.rs:113-117`); `docs/COMPATIBILITY.md` (Absatz
„The named exception: `AESGLOBAL`“) begruendet die 4-Byte-Felder mit „every
user address is below 2 GiB (VA = PA, ADR-028)“. Der Developer zitiert die
belegte Grenze, nicht eine der beiden Zahlen ungeprueft.
- `sdk/gemlib/overlay/gem.h:62-64`
- dazu beim Pruefen getroffen, derselbe Satz: `tos-api/src/aes/resource.rs:3447`,
  `tos-api/src/aes/resource.rs:4046`, `tos-api/tests/aes_rsrc_global_fields.rs:47`
  („`USER_TPA_MAX_VA` (32 MiB)“). Bei den beiden Tests pruefen, ob nur der
  Kommentar veraltet ist oder auch die Testannahme.

**3. Stack-Guard: „2 MiB GUARD“ / „exactly one 2 MiB block“** — die Sektion
reserviert **4 KiB** (`. = . + 4K;`), und `mmu.rs` macht daraus eine
ungueltige 4-KiB-Seite in einer eigenen L3-Tabelle (`refine_stack_block`,
`kernel/src/arch/aarch64/mmu.rs:303-344`, `L3_STACK` `:119-134`); „we have
only L0/L1/L2, no L3“ stimmt damit auch nicht mehr.
- `kernel/src/arch/aarch64/link-qemu-virt.ld:96-112`
- `kernel/src/arch/aarch64/link-rpi4.ld:89-90` verweist auf diesen Kommentar
  („See link-qemu-virt.ld for the layout rationale“) und bleibt richtig, wenn
  der Zielkommentar stimmt.

**4. Falsches EmuTOS-Zitat fuer `physbase`** — `tos-api/src/xbios/screen.rs:117`
nennt `bios/screen.c:1030` → `atari_physbase()`. Am Pin `1a7484ab` steht dort
das Ende von `setcolor`; `physbase()` ist
`references/emutos/bios/screen.c:1042-1049`, `atari_physbase()`
`references/emutos/bios/screen.c:917`. (Das `Logbase`-Zitat `:1071` darunter
stimmt.)

**5. „Phase 06 replaces this“** — `tos-api/src/bdos/mem/traps.rs:657-667`
beschreibt `traps::malloc` als Uebergang „until Phase 06 introduces real PDs“.
Phase 06 ist abgeschlossen; die `PF_TTRAMMEM`-Politik steht laengst im
Wrapper `tos-api/src/gemdos/memory.rs:85-106`, `traps::malloc` bleibt nur der
Pfad ohne laufenden Prozess (Kernel-Sentinel, `:92-95`). Kommentar auf diese
Rolle umschreiben.

**6. Beim Pruefen getroffen: toter Verweis** —
`kernel/src/drivers/usb/xhci/mod.rs:126-127` verweist auf `docs/STATUS.md`
„Blocked: VL805 hub configure“; den Abschnitt gibt es weder in `docs/STATUS.md`
noch im Archiv `docs/archive/status-log-2026-10-26.md`. Durch einen Verweis
auf den Commit bzw. Lauf ersetzen, der den 64-Byte-Ausrichtungsfehler belegt
