# V62 — VDI 32 planes: boot setting `vdiplanes` and the VDI depth as a boot-time value

Status: IMPLEMENTED (2026-11-18) | Priority: P2 | Commit: self | Missing: tester acceptance

Title: VDI 32 planes: boot setting `vdiplanes` and the VDI depth as a boot-time value

Type: developer, then tester. Owner decision 2026-11-18 (TASK/V61.md): both VDI depths, selectable at boot, 16
planes the default; ADR-038 is the contract for the 32-plane setting. Slice of the series V62-V69 cut from the
ADR draft of TASK/V61.md (step 2, section D). Building starts on the owner's word.

## Scope

ADR-038 points 1-3. The boot argument `vdiplanes=<16|32>` in `cmdline.txt` (absent or invalid = 16, invalid with a
boot line), read once at boot through the existing boot-switch mechanism; `planes()` becomes a boot-time value in the
three places that hold the constant 16 today (kernel raster backend, `tos-api` raster, EdDI) and at the `vq_extnd`
gate; the `vq_extnd` and device-table answers and `ap_planes` of point 3.

Sources: ADR-038 in `docs/MEMORY.md` (the contract; where it generalises an EmuTOS rule it cites the rule),
`docs/analysis/vdi-32bit-scope-2026-11-18.md` §1.2 (the change sites by file and function), TASK/V61.md step 2.
Before code: the spec files under `docs/api/vdi/` that this slice changes are extended for the 32-plane
setting (spec gate, researcher), since no EmuTOS path exists above 16 planes.

Depends on: none (first slice).

## Acceptance

- Without the argument, and with `vdiplanes=16`: every existing host test, case table and screendump is unchanged
  (byte-identical kernel behaviour is the bar: the full XBIOS and VDI case runs show no changed verdict).
- With `vdiplanes=32`: `vq_extnd` and `appl_init` report 32 planes as ADR-038 point 3 lists; an invalid value boots at
  16 with the boot line.
- The drawing result at 32 is not part of this slice (it follows in V63-V67); the slice says in its receipt what a
  32-plane boot shows until then.
- `cargo xtask test` green; both board builds; warnings delta 0; doc-check of the edited docs 0 failures.

## Spec gate (researcher, 2026-11-18) and the slice boundary

Spec: `docs/api/vdi/workstation/100-v_opnvwk.md` (section "32-plane setting and the boot argument vdiplanes"),
`docs/api/vdi/workstation/102-vq_extnd.md`, `docs/api/vdi/workstation/01-v_opnwk.md`, `docs/api/aes/application.md`.
The researcher left three points; they are settled by the ADR and this ticket's scope, no new decision:

1. `vq_scrninfo` at a `vdiplanes=32` boot between this slice and TASK/V66.md: this slice does not widen the EdDI
   gate (ADR-038 point 8 belongs to V66). The receipt states what the call answers at 32 planes until then.
2. A numeric value other than 16 or 32 is invalid: 16 planes and a boot line (ADR-038 point 2, "any other value
   counts as `Setting::Invalid`"). The boot line's wording follows the `mdlimit` line.
3. Not traced by the researcher: the order between reading the boot arguments and the first use of `planes()`.
   The developer traces it; if `planes()` is used before the arguments are read, that is a stop (BLOCKED), not a
   reorder on its own judgement.

## Slice cut corrected (lead, 2026-11-18)

The developer stopped on the spec's row for the `tos-api` raster constant (`CHUNKY_PLANES`: the `device_mem`
stamp and the `vro_cpyfm`/`vrt_cpyfm` plane cap): at 32 it doubles the row stride over the AES's 16-bit save
buffers. The researcher verified it in the code and corrected the spec (`docs/api/vdi/workstation/100-v_opnvwk.md`
§2 of the 32-plane section). That constant stays 16 in this slice at both settings and follows the setting's
depth with TASK/V65.md, which owns the raised cap and the 32-bit save buffers. The series' end state is
unchanged. In "Scope" above, "the three places that hold the constant 16" therefore reads: the kernel raster
backend's `planes()` and the `vq_extnd` gate in this slice; the raster constant with V65, the EdDI constant with
TASK/V66.md.
