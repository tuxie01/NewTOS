## The finding, measured on the Pi

Real Pi 4, kernel `c6cf484` (with the FS04 fix), probe
`measurements/measurement-2026-09-25-fs04/`, report `measurements/measurement-2026-09-25-fs04/raw/pi05-FS04-after-fix.TXT`
block 3. `QED.NAP` was copied, **502 488 bytes**, from C: to another
partition:

| | |
|---|---|
| Wall time | **5 858 ms** |
| of which copy | 5 615 ms |
| `Fwrite` | 4 753 ms |
| `Fread` of the same file | **687 ms** |
| Write throughput | **89 KB/s** |

**Reading is seven times faster than writing**, for the same amount of data
over the same bus. So the bottleneck is not the width of the path.

## Where the time goes

```
dev.write_one   n=1111  total=4784427 us  avg=4306 us  max=168270 us  min=1769us
dev.w.pio       n=1111  total=3959    us  avg=3    us
dev.w.data_done n=1111  total=4773792 us  avg=4296 us  max=168261 us  min=1760us
```

**1111 sector writes at 4.3 ms each.** Pushing the 512 bytes across takes
**3 us**; the remaining **4 296 us** are waiting until the card has written the
single sector internally. We pay this wait **per sector**, 1111 times.

## What stands structurally behind it (from the audit, with citations there)

* The driver executes **single blocks only**, although the controller can do
  CMD18/CMD25 (`emmc.rs` at the time of the audit, lines 343-345 and 353-355; the code has since moved). Broadcom on single-block in its
  own datasheet: *"resulting in long dead times"*.
* The bus runs **1 bit wide** (`ACMD6` is never sent), **without High
  Speed**, **without DMA**.
* A 32 KiB `Fwrite` falls apart below into **64 single commands**: above it
  looks like a buffer, below there is none. Counted in QEMU
  (`measurements/measurement-2026-09-25-fs04/raw/r03-driver-640x480.log`), confirmed on the Pi.
* **The limiter sits above, though**, not in the driver: the sector cache
  requests sector by sector (`blk.*_blocks max/call = 1` in **every** measured
  block). Multi-block in the driver alone changes nothing as long as the
  request above is single.
  That is the actual work of this ticket.

## What it is not

**Not** the FS04 finding. That one is fixed (2 182 → 467 ms, zero timeouts).
The audit explicitly cleared these points for the **small** file and was right:
a sector stays a sector. For 500 KB they are the whole story.

## Why it matters

The user (German original: *"so gross war die Datei nicht, dass es 3–4 Sekunden haette dauern koennen."*): "the file was not so big that it could have taken 3-4 seconds." Copying an application at the demo is more likely than waiting for a text file.

## Task

1. Measure what requests sector by sector above and what it would cost to
   bundle them: the sector cache (`tos-api/src/bdos/fs/cache.rs`) and the path
   from `Fwrite` to it (`file.rs`).
2. Only then multi-block in the driver, backed by the SD specification and
   datasheet. Before that it is ineffective.
3. 4-bit bus and High Speed are [HW04](HW04.md) and are to be measured, not
   taken along.

## Acceptance

The same copy of `QED.NAP`, throughput before/after from the same probe,
and `blk.write_blocks max/call` **greater than 1** as proof that the
bundling really arrives below.
