# V65 — VDI 32 planes: 32-plane memory MFDB: `vro_cpyfm`, `vrt_cpyfm`, `vr_trnfm`, `v_get_pixel`, screen save

Status: OPEN (2026-11-18) | Priority: P2

Title: VDI 32 planes: 32-plane memory MFDB: `vro_cpyfm`, `vrt_cpyfm`, `vr_trnfm`, `v_get_pixel`, screen save

Type: developer, then tester. Owner decision 2026-11-18 (TASK/V61.md): both VDI depths, selectable at boot, 16
planes the default; ADR-038 is the contract for the 32-plane setting. Slice of the series V62-V69 cut from the
ADR draft of TASK/V61.md (step 2, section D). Building starts on the owner's word.

## Scope

ADR-038 points 5-7: the 32-plane device MFDB (cap raised to the setting's depth), the 32-plane standard form and
`vr_trnfm`, `screen_to_mem`/`mem_to_screen` and the save buffers as 32-bit copies, `v_get_pixel` with the high word in
`INTOUT[0]` and the low word in `INTOUT[1]`, a 16-plane memory MFDB refused at the 32 setting.

Sources: ADR-038 in `docs/MEMORY.md` (the contract; where it generalises an EmuTOS rule it cites the rule),
`docs/analysis/vdi-32bit-scope-2026-11-18.md` §1.2 (the change sites by file and function), TASK/V61.md step 2.
Before code: the spec files under `docs/api/vdi/` that this slice changes are extended for the 32-plane
setting (spec gate, researcher), since no EmuTOS path exists above 16 planes.

Depends on: V63.

## Acceptance

- A pixel built from the `vq_scrninfo` description, written with `vro_cpyfm` and read with `v_get_pixel`, comes back;
  `vr_trnfm` device to standard and back is the identity.
- A 16-plane MFDB at the 32 setting is a silent no-op; at the 16 setting the 16-plane contract of ADR-024 point 4 is
  unchanged.
- Measured and recorded: the speed of the copies against today's seam (ADR-036 point 5).
- `cargo xtask test` green; both board builds; warnings delta 0; doc-check of the edited docs 0 failures.

## Spec gate (researcher, 2026-11-18) and the lead's reading of its open points

Spec landed as `65045ec90`: `docs/api/vdi/raster/_raster.md`, section "32-plane setting: memory forms, copies,
vr_trnfm, v_get_pixel, save buffers (V65)" (§1-9, change-set table in §8, acceptance table in §9), and the wide
`v_get_pixel` answer in `docs/api/vdi/inquiry/_color-pixel-input.md`.

Readings the developer works with (the acceptance criteria above are unchanged; points 1 to 3 are told to the owner
as readings of ADR-038 where it names no rule, and change if the owner says otherwise):

1. Plane counts at the 32 setting (Q1): memory forms with 1..8 planes (planar, as today) and 32 planes (chunky) are
   accepted; 9..31 are a silent no-op before any bind, 16 included (owner choice O5), also when source and
   destination are both 16-plane memory forms.
2. `vr_trnfm` at the 32 setting (Q2): the truecolor transform runs only for `fd_nplanes == 32`; 9..31 is a silent
   no-op; 1..8 stays on the planar path.
3. X byte on screen to memory (Q3): the raw store word is copied, as the 16-plane copy carries the overlay bit raw;
   tests compare `pixel & 0x00FFFFFF` for pixels that come from the screen and never assert X.
4. Slice cut, colour icons (Q4): V65 keeps the icon source 16-bit and expands each pixel at the blit; the icon
   buffers, the icon palette and the VT52 rows stay in TASK/V67.md. `blit_device_mem` therefore does not follow the
   depth stamp.
5. Order (the stop of TASK/V62.md): `bb_save_words` and the `device_mem` stamp change in one commit from one depth
   source.
6. Row stride: at 32 planes a row is `fd_wdwidth * 16` pixels; the existing stride helper multiplies by the plane
   count and must not be reused unchanged (spec §1).

Open towards the owner, not blocking the developer:

- First acceptance criterion (Q5): "a pixel built from the `vq_scrninfo` description" needs the table of
  TASK/V66.md. Until then the test can only build the pixel from the constants of ADR-038.
- Speed criterion: ADR-036 point 5 names a measurement on the real Pi 4; QEMU gives no speed figure.
- `PRESENT.NAP` builds 16-plane forms and is on the standard image: at 32 its copies are refused until its patch
  (TASK/V69.md).
