2. „beides korrigiert" ist auf beiden Profilen Wert für Wert gleich „EmuTOS" →

### D-A14-1 — der A14-eigene Defekt: der Iteratorcursor ist global · CONFIRMED

**EmuTOS:** `ORECT *w_rnext;` ist ein Feld der `WINDOW`-Struktur
(`aes/gemlib.h:85`) — **ein Cursor pro Fenster**. `wm_get` holt
`pwin = get_pwin(w_handle)` (`gemwmlib.c:1513`), wählt `pwin->w_rlist` bzw.
`pwin->w_rnext` (`:1559`), und `w_owns` schreibt `pwin->w_rnext` (`:1235`). Eine
Abfrage auf Fenster B berührt den Cursor von Fenster A nicht. **Die Spezifikation
sagt dasselbe, richtig:** `docs/api/aes/window-graphics.md:335-337`.

**NewTOS:** `tos-api/src/aes/window.rs:1054-1064` hält **einen** statischen
`RLIST { rects, count, cursor }` für die gesamte AES. `wind_get` ruft
`compute_rlist(handle)` nur im FIRST-Arm (`:2000-2002`) und danach `rlist_next()`
(`:2003`) — `rlist_next` nimmt **kein Handle** entgegen (`:1142-1155`).

**Fehlerfall, im Hostlauf gefahren, beide Profile identisch:**

    FIRST(1) -> 1, 31,  63, 296,  17
    FIRST(2) -> 1, 61, 103, 176, 114     (setzt den globalen Cursor um)
    NEXT(1)  -> 1,  0,   0,   0,   0     <-- Listenende gemeldet
    NEXT(1)  -> 1,  0,   0,   0,   0
    Soll:       1, 31,  80,  29, 162 / 1, 262, 80, 65, 162 / 1, 31, 242, 296, 15

Ein Programm, das zwei Fenster in einem Durchgang neu zeichnet (das Idiom aus
`window-graphics.md:342-346`) — oder dessen Schleife von einem Accessory
unterbrochen wird, das seinerseits `WF_FIRSTXYWH` stellt — bekommt für das erste
Fenster nach dem ersten Stück sofort das Listenende und lässt drei Viertel seiner
Arbeitsfläche stehen.

**Verdikt: CONFIRMED, quellen- *und* spezifikationswidrig. Bug, keine hinnehmbare
Abweichung.** Gefahren im Hostlauf; **nicht messbelegt**, weil die eingefrorene
Tabelle keinen verschachtelten Fall enthält (siehe Messlücken).

### D-A14-2 — NEXT prüft sein Handle nicht · CONFIRMED

Dieselbe Codestelle, andere Wirkung: weil `rlist_next()` kein Handle nimmt,
antwortet NEXT auf **jedes** Handle aus der Liste des zuletzt per FIRST
abgefragten Fensters — auch auf ein Handle, das es nicht gibt. Gefahren nach
`FIRST(1)` + zwei `NEXT(1)`:

    NEXT(7)  -> 1,  31, 80, 29, 160    Handle 7 existiert nicht
    NEXT(-1) -> 1, 260, 80, 67, 160    negatives Handle
    NEXT(99) -> 1,   0,  0,  0,   0

**Soll:** `get_pwin` liefert für ein negatives, ein zu großes oder ein nicht
benutztes Handle `NULL` (`gemwmlib.c:1395-1401`); `WF_NEXTXYWH` fällt in den
`default`-Arm der ersten `switch` und `wm_get` liefert `FALSE` (`:1521-1523`,
`:1591-1592`) — `int_out[0] = 0`, `int_out[1..4]` unberührt.

Das ist die **NEXT-Hälfte von D-A13-1** (A13 hat sie für FIRST belegt); der Ort
ist derselbe, `window.rs:1999-2010` steht vor jeder Handleprüfung. Neu gegenüber
A13 ist, dass NEXT sein Handle auch dann nicht liest, wenn es gültig ist — das
ist D-A14-1.
