# HW10 — VideoCore hardware JPEG decoder for zView's `_JPD` hook (VCHIQ, MMAL)

Status: OPEN (2026-11-12) | Priority: P3

Type: project (sources, ADR, probe, driver). Owner 2026-11-12: "also müssen wie den internen Codec Hardware decoder
ins LDG bekommen" (so we have to get the internal hardware codec decoder into the LDG); "die dokumentation dazu muss
exisitieren ansonsten hätte es auch keinen Linux treiber gegeben" (the documentation must exist, otherwise there would
have been no Linux driver); "ich gebe alle notwendigen quellen frei" (I release all necessary sources); "pack es
erstmal in ticket" (put it into a ticket for now). Software alternative: [ZVIEW05](ZVIEW05.md).

## Facts

Study: `docs/analysis/pi4-hw-jpeg-feasibility-2026-11-12.md`.

- The BCM2711 datasheet lists a JPEG interrupt source but documents no register of the block. The only path is the
  firmware service `image_decode`, reached over VCHIQ and MMAL (study §1).
- What exists is code, not a protocol description: raspberrypi/userland (BSD-3-Clause, archived 2025-08-27) and the
  Linux `vc04_services` drivers (vchiq_arm `GPL-2.0 OR BSD-3-Clause`, vchiq-mmal GPL-2.0). The Linux codec driver does
  not decode JPEG. The VCHIQ init mailbox tag `0x00048010` is not in our firmware wiki copy (study §2).
- Not known, measurable only on the Pi: whether the card's firmware provides `image_decode`, whether it decodes 24 MP,
  progressive JPEG, speed. A firmware update may drop the service (study §3, §4).
- zView's codec already calls a hardware decoder through the `_JPD` cookie (Brainstorm DSP driver interface,
  `sdk/zview/overlay/zview/plugins/jpg/jpgldg.c`, DSP path `jpgdsp.c`); NewTOS publishes no `_JPD`.
- Precedent: circle has a bare-metal VCHIQ driver (audio only, no MMAL), `references/circle/addon/vc4/`.

## Work

1. ADR: the sources the owner released, exactly as listed in study §7 (pinned commits); read as specification, no
   code copied (clean-room; GPL-only files are read, not copied). Pin them into `references/`.
2. Probe kernel (debug feature, like SND03): VCHIQ transport up through the mailbox tag, open the MMAL service, query
   `image_decode`, decode the owner's 24 MP picture once and time it. Real-Pi run with the owner.
3. Only if step 2 succeeds: VCHIQ/MMAL driver in the kernel, a `_JPD`-compatible decoder interface for native programs
   (spec first, from the zView codec's use of it), wiring in the JPG codec; fallback to software when the firmware
   refuses (progressive, size).

## Acceptance

- Step 2 answers presence, size limit and speed on the real Pi (run).
- After step 3: `IMG_4831.jpeg` opens in zView via the hardware path, faster than the ZVIEW05 software path (measured),
  and a picture the hardware refuses still opens in software.
