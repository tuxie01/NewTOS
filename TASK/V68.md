setting (spec gate, researcher), since no EmuTOS path exists above 16 planes.

## Spec gate and documents (researcher, 2026-11-18) and the lead's reading

Landed with the documents of this ticket: `docs/api/xbios/58-vsetmode.md`, `docs/api/xbios/5b-vgetsize.md`,
`docs/api/xbios/04-getrez.md` (section "At the 32-plane setting" in each), `docs/COMPATIBILITY.md` (section "The VDI
device depth: 16 planes by default, 32 planes by a boot setting"), `docs/DEVIATIONS.md` (section "VDI at 32 planes").
Read from the code: none of `Getrez`, `VsetMode`, `VgetMonitor`, `VgetSize` reads the VDI depth; the code does not
contradict ADR-038 point 9.

Left for the developer (lead's slice cut; the acceptance criteria above are unchanged):

1. A host test that the XBIOS video answers are identical at 16 and 32 planes and equal the known values
   (`VsetMode(-1)`, `Getrez`, `VgetMonitor`, `VgetSize` with and without framebuffer, `VgetRGB`, `VsetMode(0)`,
   `Vfixmode`).
2. `cargo xtask tosdump` gets an option for extra boot arguments. Today it passes a fixed `serial=on`, so a case run
   at `vdiplanes=32` (first acceptance criterion) is not possible through it; the testers of TASK/V62.md to
   TASK/V67.md each patched that in their own tree. Without the option the default call is unchanged.

Notes for the tester (method, not criteria): the XBIOS video cases are in `tosdump/cases/bios-r1.tsv` (`Getrez`,
cases 211-215); run the table at the default and at `vdiplanes=32` and compare the two NewTOS dumps cell by cell;
case 213 differs from the oracle by design (accepted with TASK/XBIOS22.md).

The wording "memory forms with 9..31 planes are refused" in the two documents is the reading of TASK/V65.md
(ADR-038 names the 16-plane form only); told to the owner on 2026-11-18, no objection.
