PROOF THAT EMUTOS READS THE TEST IMAGE ITSELF (runs/controls/trace/)
  trace.txt = Hatari's trace; ide-and-os-calls.txt = method/ide-commands.py of it (IDE commands with
  LBA from the task-file registers -- Hatari's own "IDE: read sector=N" lines agree -- interleaved
  with the BIOS/GEMDOS calls and Hatari's routing lines):
    IDE READ MULTIPLE drive 0 LBA 0 (MBR), LBA 63 (boot sector; first data words eb3c 904d 544f 4f34
    = the file's bytes at 0x7E00), then
      GEMDOS Fsfirst("\AUTO\*.PRG") -> BIOS Getbpb(2) -> IDE LBA 63
      -> BIOS Rwabs(0,...,1,257,2) -> IDE READ MULTIPLE LBA 320 (root directory: 63+1+2*128 = 320)
    No IDE write command in the whole run.
  Hatari's GEMDOS layer on C:: every C: call is "-> to TOS" except the desktop's first
  Fopen("C:\EMUDESK.INF"), answered "-> FD 64" by Hatari's --auto INF override (a host file; no IDE
  access, image unchanged); the second Fopen of it after the dumper is "-> to TOS". All D: paths
  "-> host".
  Byte order: swap-auto/ide-and-os-calls.txt shows the same words as trace (file order);
  swap-on/ide-and-os-calls.txt shows 3ceb 4d90 4f54 344f, byte-swapped, and EmuTOS' answers are unchanged
  (it detects the swapped MBR and swaps back, bios/disk.c:867-870).
