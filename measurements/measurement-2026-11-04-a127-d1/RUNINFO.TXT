measurement-2026-11-04-a127-d1 -- A127 D1: the menu tracker takes the left button as events
==========================================================================================
Developer, TASK/A127 (divergence D1 only), 2026-11-04 (host clock CET). Base HEAD 4d44a616 plus
the uncommitted D1 change in the working tree (tos-api/src/aes/menu.rs track/track_owned,
tos-api/src/aes/input.rs post_button/mn_button_arm/mn_button_take/mn_button_cancel). QEMU only:
raspi4b (headless, -append serial=on, scripted IKBD injector) and virt (xHCI + usb-mouse over
QMP). No real Pi, no real card, not committed. QEMU 11.0.2.

WHAT / WHY
  A127 run C (measurements/measurement-2026-11-04-a127/RUNINFO.TXT) showed that a press+release
  decoded in one pump pass was lost by menu::track (it sampled vdi::mouse_buttons() once per
  pass; EmuTOS mn_do waits for button events, aes/gemmnlib.c:356,369-376). D1 makes each round
  of the tracker arm a button wait that post_button completes with the first published
  transition it accepts (docs/api/aes/menu.md "Mouse ownership over the track", point 9).
  This run repeats A127 runs C, A, B (injector, raspi4b) and E, F (real USB path, virt) on the
  D1 kernel: C must act on the first fast click; A, B, E, F must behave as before.

CAVEATS
  QEMU has no Pi timing; 5 ms injector grid. Behaviour change that comes with D1 and is
  EmuTOS's: while a multi-click wait is pending (gl_bpend, e.g. the desktop's double-click
  wait), a press on a menu item opens the double-click window (b_click, aes/geminput.c:133-140)
  and the menu acts when the window publishes it (default 220 ms, at once on a move of more
  than 2 px) -- before D1 the tracker acted on the raw level at once. Visible in run C/A only
  as "dialog in the next screendump". Not checked on the real Pi.
