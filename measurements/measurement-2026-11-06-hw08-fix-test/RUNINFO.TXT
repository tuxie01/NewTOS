8  DRIVER CHANGE OUTSIDE THE BRIEF (kernel/src/drivers/bcm2711/emmc.rs, emmc_xfer.rs; diff read in full, then measured)
   What it does (read): (a) a data command that gets no answer (unanswered CMD24/25/17/18) now takes BOTH software resets (Phase::resets(status, data_cmd), DATA_CMD_ARMED set in command()
   only for CMD_ISDATA commands, cleared on Command Complete); (b) after an error the recovery asks CMD13 (card_state) and sends CMD12 only when the card is in rcv/data; (c) the next data
   command waits in wait_card_ready, but ONLY if CARD_NOT_READY was set by a recovery -- at most WRITE_BUSY_MS (1000 ms); (d) ILLEGAL_COMMAND in an R1 of a data command no longer counts as refusal.
   Boot: init() runs once (kernel/src/lib.rs:420, idempotent, no re-init path; grep: no other caller than the selftest). Both new statics start false. During identification SDCARD.ready is false:
     recover_inner then keeps the old `else if abort { abort_transaction }` branch; the only change at boot is for a failing data command during identification (ACMD51): both resets instead of
     the CMD reset -- more thorough, never less. Measured: the [emmc] lines of the serial log of base and fix are identical in 3 compared rounds (rounds 0, 3, 6), "M1 during identification: 2
     error(s), 0 timeout(s), 2 recovery(ies) CTO=2" on both = the QEMU baseline, unchanged by the fix.
   Boot time, QEMU raspi4b, kernels alternating, same card, 7 rounds each (method/boottime.py, results/boottime): base min 15.14 median 15.17 max 15.18 s, fix min 15.14 median 15.18 max 15.19 s.
     HONEST CAVEAT: the figure is dominated by a fixed boot-screen delay (every run 15.1-15.2 s), so it cannot resolve an SD-init difference of a few ms; what resolves it is the identical
     emmc log and the identical recovery counters, not the wall clock.
   Card without errors: the sd-diag line at the end of the healthy n1 run (about 1350 writes after / 2930 before): "errors 2 timeouts 0 recover 2 nonrecover 0 refused 0" on both = the two boot
     recoveries only; wait_card_ready and the CMD13 path never ran (CARD_NOT_READY false). The only per-command cost on the healthy path is two relaxed atomic stores in command().
   Media change: the driver has no card-detect and no re-init after boot (see above), a card swapped under a running system is not noticed by this driver before or after the fix; so there is
     nothing for the new flags to go stale across. (Not verifiable in QEMU either: no hot-swap on this path; I did not try a QMP change-medium.)
   Failure paths (QEMU injection, the developer's modes, reproduced in 3): t1, t2, d1 (transfer running: CMD13 rcv, CMD12 + resets): R1-R4 ok; u2-u6, w1 (formerly driver dead): R1-R4 ok after the
     busy; p1-p4 (card in prg simulated): p1 one -2 then ok, p2 2.6 s -2,-2 then ok, p3 FAT: Fclose -2, file complete, p4 sustained (all four saves -2 while armed, R1-R4 ok). Worst case per access
     with a card that stays in prg: wait_card_ready up to 1000 ms + the failed command: a dead/stuck card costs about WRITE_BUSY_MS (+100 ms RECOVERY_MS in w1) per access, bounded, no hang (w1 runs
     to its end). That is the developer's "bei toter Karte kostet jeder Zugriff die Wartezeit".
   Not verifiable here: whether the resets work on EMMC2 for a real card, a real card's reply to CMD13 in prg/tran, anything on silicon (HW checklist; the developer's Pi plan PI-RUN.TXT is the way).
   One thing that could degrade, found while reading: ILLEGAL_COMMAND is now ignored for EVERY data command, not only the one that followed our own abort -- a command that is really illegal in
     the card's state goes unanswered per the spec (SD Phys 4.6.1) and ends as a timeout instead of an early refusal; the outcome (error to the app) is the same, the delay is up to one command
     timeout. Not measurable in QEMU; named, not measured.
