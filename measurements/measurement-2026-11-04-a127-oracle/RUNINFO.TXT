WHY A NEW PROBE, AND HOW THE MOUSE GETS IN
  Hatari 2.6.1 (the pin) cannot inject a left button or a mouse motion: its --cmd-fifo "hatari-event"
  knows doubleclick, rightdown, rightup, keypress/keydown/keyup only (Hatari v2.6.1 src/control.c
  Control_InsertEvent, `git show v2.6.1:src/control.c` in a Hatari clone; the pinned binary's strings
  contain no "leftdown"; leftdown/leftup/mousemove exist only in a later, unreleased commit 5ac6a7b3).
  Two documented substitutes were used, and they agree (results, section 3):
  (a) PRIMARY, the probe's own feeder (EmuTOS side): an etv_timer hook (Setexc 0x100, chained, runs every
      4th Timer-C tick) passes the script's IKBD relative mouse packets to Kbdvbase()->mousevec with
      a0 = packet, exactly as EmuTOS's call_mousevec does (references/emutos/bios/aciavecs.S:538-553;
      EmuTOS itself calls it from Timer C for the Alt-arrow repeat, bios/ikbd.c:518-523). Same script
      bytes as NewTOS's injector (tools/inject-arm.py launch:MNPROBE feeds them to kernel/src/ikbd.rs
      feed). Side effect: the feeder runs in the same Timer-C interrupt just BEFORE the AES tick
      (vdi/vdi_misc.c:76-83 tim_addr chain), so every injected press lands at the same phase of the
      20 ms AES tick -- the oracle value is phase-locked (the lowest possible value minus one, see 3.2).
  (b) CROSS-CHECK through the real IKBD interrupt path: Hatari --cmd-fifo keydown/keyup of Alt + arrow
      keys / Alt + Insert = EmuTOS's keyboard mouse emulation (bios/ikbd.c:285-389: 8 px per Alt+arrow
      make, Alt+Insert = left button down/up, sent through call_mousevec). Wall-clock timing, so the
      press arrives at a random phase of the AES tick. The probe's passive mousevec observer (V-lines)
      records _hz_200 of every packet the mouse vector receives.

3.2 Resolution. The window counts down in 20 ms AES ticks (EmuTOS gl_dclick = rate/gl_ticktime:
  275/20 = 13, 220/20 = 11, aes/gemevlib.c:33,300-308; b_delay per tick, aes/geminput.c:150-171),
  so the press -> publication time is n*4 hz_200 ticks minus the press's phase within the AES tick:
  48..52 for index 2, 40..44 for index 3. The feeder fixes the phase at its minimum (it runs in the
  same Timer-C interrupt right before the AES tick): 48 / 40 every time; through the real IKBD
  interrupt (random phase) the oracle spreads over 49..52 / 41..44. NewTOS head's AES tick is its
  monotonic clock in 20 ms steps (tos-api/src/aes/input.rs now_tick), its phase changes per boot:
  head gives 48..52 and 40..44 -- every head sample lies inside the oracle's band. Base: 0 always.

3.3 Message-only wait with no multi-click wait before it (probe v2, MNPROBE.MFS: order M, D2, M, D2, D1;
  INF #E 1A):
    EmuTOS tt (feeder)    click M: 0 0 0 0 0   click D2: 48 x5   click D1: 48 x5
    NewTOS head           click M: 0 0 0 0 0   click D2: 51 x5   click D1: 51 x5
    NewTOS base           click M: 0 0 0 0 0   click D2: 0 x5    click D1: 0 x5
  So the delay is not tied to the program's current wait: EmuTOS opens the double-click window for
  every press while gl_bpend > 0, and a bclicks > 1 wait that ends with a message leaves its increment
  behind (aes/geminput.c:477-479 decrements only when the button satisfies it, :559-561 increments;
  docs/api/aes/event.md "The double-click window" states this). Before the first D2 wait: no window, on
  both sides; after it: the window, on EmuTOS and head, never on base.

3.6 Other observations
  - evnt_multi returns: EmuTOS and head return exactly once per selection in the default order (25);
    base returns 175-179 extra MU_BUTTON events (bstate 1) per run: it publishes the selection at the
    press, the program's next D2/D1 wait then finds the button still down and is satisfied over and
    over until the release (analysis/returns.txt). EmuTOS does the same when the selection really comes
    at the press: v2 M-first, the switch from M to D2 at the 5th selection gives 16 MU_BUTTON returns
    on EmuTOS, 35 on head (the count depends on how many evnt_multi round trips fit into the 50 ms
    hold, i.e. on CPU speed; base: 168).
  - INF without #E: NewTOS reports evnt_dclick 3 (= EmuTOS's AES default ev_dclick(3), aes/geminit.c:708);
    not measured on EmuTOS (Hatari's --auto always writes an INF with #E).
  - Geometry equal on both sides: graf_handle 8 16 19 19, objc_offset of title/items equal (O-lines).
  - No AES input trace: the parameters that arrived are not checked by an instrument on either side
    (aes-trace flushes only after a >= 3 s idle wait, the probe never has one; Hatari has no AES argument
    trace). The binding is the tosdump td_abi_aes backend of every AES probe; the D2/M/D1 behaviour
    differs as the arguments predict on both sides (MU_BUTTON returns only in D2/D1, M-first 0).

VERDICT: CONFORM. NewTOS head (bae52dbd) matches EmuTOS within the measurement resolution (one 20 ms AES
tick): click-select ends 48-52 ticks (index 2) / 40-44 ticks (index 3) after the press on both, in the
desktop's wait, in a message-only wait after a double-click wait, and with bclicks 1; 0 in a message-
only wait before any double-click wait on both; drag-select 0 after the release on both. NewTOS base
(4d44a616) diverges: 0 ticks whenever EmuTOS waits for the double-click window, plus the MU_BUTTON
burst. The tester's 40-42 ticks on head (desktop, QED; NEWDESK.INF without #E = index 3) are inside the
oracle's 40-44 band for index 3.
