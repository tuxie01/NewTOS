XBIOS06 step 1 -- rsprobe: Rsconf and the Iorec(0) record on the oracle (tt, falcontc) and NewTOS -- 2026-10-30
==============================================================================================================
Developer run for TASK/XBIOS06.md, "Arbeit, Schritt 1" (probe and measurement only, no product code),
user decision 2026-10-30 point 2 ("Erst messen, dann fixen"). Case design: docs/analysis/xbios06-rsconf-profile-2026-10-30.md

No hardware, no real card, nothing flashed. Not committed (the lead commits).

WHY
  The owner's open questions before the fix (analysis section 4, ticket decision point 2):
    1. TSR semantics on the oracle when the program writes tsr 0x00 / 0x08 / 0xFF (S19-S21): what does
       Rsconf(-1 x6) read back?
    2. P16: where does Rsconf(-2) answer from -- the Iorec(0) record or a shadow? (The probe writes the
       record's baudrate, then asks.)
    3. Which Iorec(0) fields does EmuTOS write on tt vs falcontc after Rsconf (baud/flow in and out of
       range, ucr variants)?
    4. Every line where NewTOS differs.
  Why a probe and not a tosdump table: DUMPBIOS refuses every Rsconf with a baud rate set
  (tosdump/core/cases.c:4050-4055@CR_RSCONF); the follow-up that moves the cases to tosdiff is TASK/TOOL27.

METHOD (method/)
  run-all.sh       the six runs: tosdump/probes/run-rsprobe.sh twice per side (emutos tt, emutos falcontc,
                   newtos <kernel8.img>), RSPROBE_SCRATCH set to the session scratchpad
  trace-check.py   the input check on NewTOS: the [biostrace] lines of caller U0 in BOOT-SERIAL.txt against
                   the call sequence the probe source gives (Iorec(0), then per step line the step call,
                   Rsconf(-2 ..), Rsconf(-1 x6)); each argument's low 16 bits and each 64-bit result
                   against the log. Negative-tested by hand (a changed argument and a changed return in a
                   copy of the log each give FAIL); not kept.
  compare.py       field-by-field comparison of the three sides -> runs/compare.txt
  Probe            tosdump/probes/rsprobe.c (permanent, committed with this run, CLAUDE.md "Testing" probe
                   rule), one source for both sides, mintlib osbind.h bindings. Line layout and step order:
                   the probe's header comment. Iorec(0)'s five UBYTEs are read in user mode at the offsets
                   of the tosdump-layout block in docs/api/structures/iorec.md (m68k 28..32, LP64 48..52);
                   line L00 checks the offset base against 2*sizeof(_IOREC) (ok=1 on all sides). The
                   probe's record writes (P16 baudrate := 7, P18 restore) run in a Supexec callback, as
                   mdprobe's ring feed does.
  Runner           tosdump/probes/run-rsprobe.sh (committed, not copied here), the run-mdprobe.sh pattern
                   without the HOLD wait (the probe terminates): Hatari stops once RSPROBE.LOG holds
                   "Z99 end"; QEMU once the shell prints "RSPROBE.NAP' exited with rc". NewTOS card:
                   tools/mkcard.sh (C:\RSPROBE.NAP, NEWDESK.INF "#R 02" + "#Z 01 C:\RSPROBE.NAP@"), booted
                   as an APFS clone.
  hi on m68k: the probe prints the high half of (long long)(long)r -- on m68k the sign extension of d0
  (m68k has no 64-bit register); on NewTOS the high half of x0. Same convention as mdprobe/xcprobe.

ANSWERS (measured [M]; derived, not read or measured directly [D])
  1. TSR on the oracle, Rsconf(-1 x6) read-back after a write:
       tt:        0x00 -> 0x80, 0x08 -> 0x88, 0xFF -> 0xFF, restore 0x81 -> 0x81 [M]
                  [D] every measured value fits "read = written | 0x80"; bit 7 read 1 in every read on tt,
                  bits 0-6 read as written in all four writes. Hatari's MFP model, not a real MC68901.
       falcontc:  0x00 -> 0x00, 0x08 -> 0x08, 0xFF -> 0x08, restore 0x00 -> 0x00; wr5 bit 4 follows tsr
                  bit 3 (ea -> fa -> ea) [M] -- as rsconf_scc reads (references/emutos/bios/serport.c:788-790,
                  846-859)
       NewTOS:    0x00 -> 0x00, 0x08 -> 0x08, 0xFF -> 0xFF, restore 0x01 -> 0x01 (read = written) [M]
  2. P16, Rsconf(-2) after the program set Iorec(0)->baudrate to 7 (shadow/hardware at baud 4):
       tt 7, falcontc 7 (the record; references/emutos/bios/serport.c:222-223, :779-780) [M]
       NewTOS 4 (its shadow RS_BAUD, tos-api/src/xbios/system.rs:263@RS_BAUD) [M]
  3. Iorec(0) fields EmuTOS writes in Rsconf:
       tt:        baudrate (only 0..15: 16 and -3 keep it), flowctrl (only 0..3: 4 and -2 keep it); ucr,
                  datamask, wr5 stay 88/ff/ea through every ucr write (P12-P15) [M]
                  (references/emutos/bios/serport.c:231-232, :237-238)
       falcontc:  baudrate and flowctrl with the same ranges; plus ucr (= the written ucr), datamask
                  (0x28 -> 7f, 0x48 -> 3f, 0x68 -> 1f, 0x98/0x88 -> ff), wr5 (bits/char: aa, ca, 8a; break
                  bit 4 from tsr bit 3) [M] (references/emutos/bios/serport.c:792-793, :798-800, :811-832,
                  :846-859)
       NewTOS:    none -- the record stays 01 00 88 ff ea through every Rsconf (P01-P15); only the
                  program's own write (P16) changes it, and P17's Rsconf(1,..) does not set it back [M]
  4. NewTOS differs on every step line (table above): against tt in the TSR byte (01 vs 81) and the high
     half, plus Iorec(0) baudrate from P01 on (except where the value is 01) and flowctrl from P08 on,
     plus P16 (answer 4 vs 7) and P18 (restore needed). Against falcontc: the same high half, record
     baudrate/flowctrl and P16/P18 lines; the RSR byte (01 vs 00); the TSR byte (NewTOS reads back what
     was written, falcontc only bit 3: 01 vs 00, FF vs 08); wr5 at S20/S21; and from P12 on
     ucr/datamask/wr5 of the record.
     Where NewTOS equals tt: every ucr/rsr byte of ret/g; the TSR byte of S21's read-back and S21r's
     return (0xFF on both); every Rsconf(-2) answer q except P16; baud/flow range checks as seen through q.
