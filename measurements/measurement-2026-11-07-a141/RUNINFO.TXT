THE USER'S THREE QUESTIONS, each measured
  Byte order (shapes or masks torn, shifted by 8 pixels): NO. M* equal on both sides; I* equal. Hand decode of the file without any NewTOS code
    (method/palette-test.py, tools/mkrsc.py read_cicon_table only) gives untorn shapes in every variant (analysis/sheet-*.png).
    tools/mkrsc.py swaps every raster on conversion, the loader reads native words: equal I*/M* to the oracle's big-endian words prove it.
  Palette or pen mapping that does not fit the icons (shapes right, colours wrong): YES, and it lies in the resource, not in NewTOS' mapping.
    Per pixel, the file's 4-plane variant states what the pixel is meant to be. The 8-plane index at the same place (5480 pixels):
      index 252  n=1381: 4-plane dark grey 1291    EmuTOS palette (267,133,0) brown
      index 250  n=656:  4-plane white 656         EmuTOS palette (267,267,0) olive
      index 229  n=68:   4-plane white 68          EmuTOS palette (467,67,0) brown-red
      index  93  n=103:  4-plane dark red 97       EmuTOS palette (67,1000,0) bright green
    Mean RGB distance to the 4-plane picture (analysis/palette-scores.txt; a coarse reduction, the ranking is the result):
      EmuTOS default palette 368.0; references/freemint/xaaes/src.km/pal/gem.pal 314.9; references/freemint/xaaes/src.km/pal/nvdi.pal 133.8.
    analysis/sheet-nvdi-reg-to-pen.png: the same 8-plane bytes under FreeMiNT's nvdi.pal: grey frames, orange folder and floppy arrows, blue
    arrows, red X, grey floppies. That is what the artist drew. analysis/sheet-emutos-default.png: what EmuTOS and NewTOS draw.
    FreeMiNT knows the problem: XaAES has `remap_cicons` and `icn_pal_name = nvdi` (references/freemint/xaaes/src.km/xa_rsrc.c:261-300,
    references/freemint/xaaes/src.km/example.cnf:609-630). EmuTOS has no such thing: transform_cicon takes the plane value n to
    phys_work.ext->palette[n] (references/emutos/aes/gemrslib.c:348-396), the default palette (references/emutos/vdi/vdi_col.c:137).
    The pen mapping itself is right: reading the index as a register (EmuTOS, NewTOS) gives black outlines, reading it as a pen gives
    magenta ones; nvdi.pal scores better through the register mapping too (133.8 vs 168.9). A resource can carry its own palette; this
    one does not (extension array 25754, 4590, 0, ...).
  Plane order: NO. Plane p = bit p in the hand decode gives the clean pictures above, and I* are equal to the oracle.

NOT THE SAME BETWEEN THE TWO HYPVIEWS, and not an OS difference
  Rows 65..68 under the disabled icons: NewTOS' toolbar has dither bars there, the m68k HypView's has none. Upstream's resource makes each icon
  object 32 pixels high (ob_height 0x0020), the m68k one 21 (0x0105 = 1 char + 5). icprobe gives 0 differences for each resource on the two
  systems, so it is the file. The bars are in the report's photo too. That m68k binary also panics with upstream's resource because the object
  order in the tree differs: its code assumes another numbering, runs/oracle-hypview/falcontc-upstream-rsc-crash.

A142, SAME ROOT? NO
  Another path, another fault. qed.rsc has no colour icons at all (vrsn 0). The photos' check boxes, radio buttons and alert icon are cflib's
  built-in images: sdk/cflib/overlay/inline.rsh declares them `static _UBYTE inline_IMAGE0[]` etc. in m68k byte order, casts them to words, and
  cflib/userdef.c hands them to vrt_cpyfm as `short *`. On a little-endian machine each word's two bytes are swapped.
  analysis/a142-inline-images.txt: the four alert images stand unchanged in sdk/apps/qed/build/QED.NAP
    (274986f02cecb77c49a9ed523008473b25e16b672452cb641b1b08e0e73fd56f).
  analysis/a142-cflib-images-be-left-le-right.png: left big-endian, right the same bytes as little-endian words: the right "!" is the torn icon of
  photos/issue21-alert.png. photos/issue21-radio.png, issue21-check.png show the same left/right swap on the BT_RADIO/BT_CHECK data.
  Upstream file, our build: this is a build-side byte-order defect in our cflib port, in reach of sdk/cflib/overlay/. Not reproduced in QEMU here and
  not fixed: TASK/A142 stays its own ticket.
