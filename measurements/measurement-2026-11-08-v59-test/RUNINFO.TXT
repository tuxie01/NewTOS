FP-CONTEXT (ADR-036 point 3) -- the pointer is also drawn from the timer IRQ, checked in code
 (a) EL0 registers survive: rust_irq_handler (kernel/src/drivers/gic.rs:201@rust_irq_handler) -> host_env::irq_input_pump (kernel/src/host_env.rs:567@irq_input_pump) ->
     pump_devices_irq -> ikbd feed_relative -> mouse erase/draw -> copy_rows / expand. When the IRQ interrupted EL0 the V registers hold the program's live values; no
     other code between the exception entry and the kernel touches them (soft-float target, module note of kernel/src/raster_kernel.rs; the disassembly shows no V use
     outside the five kernels listed in result 1 and the six context-switch functions). Each kernel stores every V register it names to a stack save area first and loads
     it back before its block ends (result 1: per-region saved == restored). save_fp_context/restore_fp_context run only on synchronous svc paths (callers
     kernel/src/arch/aarch64/exceptions.rs:1090@save_yield_frame, :1332@apply_switch, :1715@finish_terminate, :2318@handle_pexec), none from the IRQ path.
 (b) no NEON kernel can be underneath that draw: the pump returns at once unless the IRQ came from EL0 (host_env.rs:572-575 `if !from_el0 { return; }`, input_gate.rs:144@spsr_is_el0,
     :135@irq_pump_allowed requires from_el0 and process and upcall_depth == 0 and !aes_suspended); IRQs are masked on every exception entry, and gic.rs:224 runs the pump
     "still with IRQs masked", so the pointer draw from the IRQ cannot be nested in another kernel. The sites that unmask IRQs at EL1: host_env.rs:109 and :154 (the
     one-pass pump_input and console_read_byte_blocking waits, daifclr #2 ... restore DAIF), host_env.rs:611 (read_key_loop), console.rs:237 (aux_read_blocking), and
     gic::enable_irqs (gic.rs:278). Inside those windows the trap-side pump (pump_devices -> USB poll -> ikbd -> pointer draw -> NEON kernel) CAN run with IRQs unmasked,
     i.e. a timer IRQ can land inside a raster kernel at EL1 (SPSR from EL1). Then irq_input_pump returns at once (not from EL0), so no second pointer draw; what still runs
     in that IRQ is the timer, the PL011 drain and fbcon::blink_tick (gic.rs:226-228, tos-api alpha_blink via try_lock), which may draw the text cursor through the backend (the raster_kernel.rs
     note says through the scalar row methods; I did not trace it) -- were it a NEON kernel, it saves and restores its registers on its own stack area, so the interrupted kernel's values are handed back; the V
     registers are not corrupted either way. (Pre-existing since V49, not changed by V59; pixel-level interleaving of a blink with a pointer paint in that window is a
     separate, unmeasured question -- out of scope.)
     Verdict on the finding: confirmed from the code and the disassembly; not exercisable in QEMU as an EL0 register-survival test (no EL0 program checking v0-v31 across
     pointer motion was run) -> an open item: Pi-side, the INPUT01 path with a hard-float EL0 program is the only direct test.
