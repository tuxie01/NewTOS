CAUSE, with evidence (analysis/find_file-disasm.txt)
  pc - basepage = 0x7eac, in find_file (static, sdk/apps/hypview/file.c): `ldr x21, [x8, #0x88]`, x8 loaded from the GOT slot
    0x34cb8 -> Win. 0x88 = offsetof(WINDOW_DATA, data). This is `DOCUMENT *doc = win->data;` under `if (win)`.
  x30 - basepage = 0x7de0, the return address of `bl find_file` in OpenFileNW.
  x0 = basepage + 0x36840 = last_path. Only DoUserEvents (sdk/apps/hypview/dl_user.c, AC_OPEN branch) calls
    OpenFileNW(last_path, ...), under count_window() == 0 && last_path[0] != 0: the accessory's reopen. The WM_CLOSED branch
    of the same function fills last_path when the last window closes. The report's two photos carry the same x0, x30, pc.
  Who frees: red-fsio serial, slot 0 (the accessory):
    000198 gemdos 0x44 ret=28381184      Mxalloc -> 0x1b11000, x8 of the crash: OpenWindow's WINDOW_DATA (dl_win.c)
    000302 aes 25                        evnt_multi returns WM_CLOSED
    000306 aes 12, 000307 aes 102, 000309 aes 74, 000311-313 gemdos 0x49 x3   appl_write, wind_close, shrinkbox, CloseFile
    000314 aes 103, 000316 gemdos 0x49   wind_delete, then Mfree: RemoveWindow's order (dl_win.c), this frees 0x1b11000
    000359 aes 25                        evnt_multi returns AC_OPEN
    000360 aes 78                        graf_mouse(BUSYBEE), first line of OpenFileNW after the empty-path test
    then the fault in find_file, before any further trap.
    fs-io-trace does not print Mfree's argument; that 000316 frees this block follows from the source order and from the
    crash report's "pool yes, no block".
  Why `Win` still points there: HelpWindow (sdk/apps/hypview/window.c) starts with `Win = win = p;` on every call, also for
    WIND_EXIT, whose branch ends with `win = NULL` on the local variable. Nothing clears the global. PopupWindow (hyp/popup.c)
    does the same. As a program HypView leaves its loop with the last window (hyp_view.c: `while(!_app || ...)`), so upstream
    never reads Win again; as an accessory it loops on.
  HypView IS meant to run as an accessory: hyp_view.c registers with menu_register when !_app, dl_user.c handles AC_OPEN and
    AC_CLOSE and keeps last_path/last_node for the reopen. Between openings it frees every window and document (RemoveWindow,
    CloseFile) and keeps its resource, VDI handle and configuration.
  EmuTOS: xmfree (references/emutos/bdos/umem.c:135-155) -> freeit (references/emutos/bdos/iumem.c:144-221) move the MD from the
    allocated to the free list and do not touch the block, so the read returns stale but intact data and the program runs on
    by luck, unless the block has been reused. Not measured on the oracle: HypView here is an LP64 build. The memprot=off
    control shows the same sequence with the block readable.
  NewTOS: freed pages lose their mapping (docs/COMPATIBILITY.md, section on memory protection, observable difference (1),
    ADR-027); FreeMiNT does the same (references/freemint/sys/memory.c:930-932, mark_region PROT_I). The kernel is right; it
    stays unchanged. Its report was accurate: model=invalid table=invalid table==model.

FIX sdk/overlays/hypview/dl_win.c, three lines against upstream, header says why
  `if(Win == ptr) Win = NULL;` before the two Mfree(ptr) that follow a proc call (RemoveWindow, OpenWindow's failure path).
  NULL is Win's state before the first window, and find_file, OpenFileSW and block.c handle it. Win is compared before the
  free. Other windows' Win is left alone. A popup's removal leaves Win NULL until the next event of the main window sets it.
  Why not in window.c: popup.c stores Win as well, and a nested popup removal would need a third site.
