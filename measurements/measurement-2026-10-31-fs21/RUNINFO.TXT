WHAT / WHY
  Finding of FS20 (measurements/measurement-2026-10-28-fs20/RUNINFO.TXT), seen again in TOOL20 and
  FS24: after Fcreate/Fwrite/Fclose the file's directory entry has attribute 0x20 (FA_ARCHIVE) on the
  oracle, 0x00 on NewTOS. TeraDesk shows and uses the bit (sdk/apps/teradesk/dir.c:1864,
  sdk/apps/teradesk/copy.c:1617).

THE EMUTOS RULE (read from the source; spec docs/api/gemdos/file/3e-fclose.md edge case 8)
  ixclose rewrites the entry only when the DFD is O_DIRTY (references/emutos/bdos/fsopnclo.c:530); it
  reads the attribute the entry has at that moment (:537), copies time/date, start cluster and length
  from the DFD (:538-540), ORs FA_ARCHIVE in for a file (:544-545; a folder closed CL_DIR gets length 0
  and no bit, :542-543) and writes the byte back (:547-548). O_DIRTY is set by Fcreate
  (references/emutos/bdos/fsopnclo.c:206), a write that grows the file (addit,
  references/emutos/bdos/fsio.c:42-46) or gives it its first cluster (nextcl,
  references/emutos/bdos/fsfat.c:279-282), an Fdatime set (references/emutos/bdos/fsdir.c:698) and the
  cross-directory Frename of a file (references/emutos/bdos/fsdir.c:1066, NewTOS had that already).
  Not dirty: open, read, seek, a write inside the length, Fdatime get. Fattrib writes the entry directly
  (references/emutos/bdos/fsdir.c:424-432); a later close ORs into that value.
