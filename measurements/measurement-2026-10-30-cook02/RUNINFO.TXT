measurement-2026-10-30-cook02 -- COOK02 country facts: where the oracle's _AKP 0x0100 and _IDT 0x112E come from
==============================================================================================================
Researcher, 2026-10-30 (host clock CET). Tree HEAD 60824ec8 (main) with other tasks' uncommitted changes

WHAT / WHY
  TOOL18 measured _AKP = 0x00000100 and _IDT = 0x0000112E on the pinned EmuTOS 1a7484ab (a `make 512
  COUNTRY=de` ROM). The source read (docs/analysis/cook02-country-facts-2026-10-30.md section 3) explains
  both from Hatari's default NVRAM: byte 7 (keyboard) = 0, bytes 8/9 (IDT) = 0x11 0x2E, and EmuTOS built
  with CONF_MULTILANG 0 takes the display country (high byte) from the OS header (DE = 1) and only the
  keyboard (low byte) from NVRAM. This run tests that explanation: the same jar table, same ROM, same
  Hatari, with Hatari's [Keyboard] nKbdLayout / nLanguage set (Hatari copies them into NVRAM bytes 21 / 20
  when they are not -1: Hatari src/falcon/nvram.c NvRam_Init). Prediction written BEFORE the runs:
    base       nKbdLayout -1, nLanguage -1  -> _AKP 0x0100
    kbd1       nKbdLayout  1, nLanguage -1  -> _AKP 0x0101   (keyboard byte follows NVRAM)
    lang2      nKbdLayout -1, nLanguage  2  -> _AKP 0x0100   (language byte ignored: CONF_MULTILANG 0)
    lang2kbd2  nKbdLayout  2, nLanguage  2  -> _AKP 0x0102
    _IDT 0x112E in all four (NVRAM bytes 8/9 untouched).
