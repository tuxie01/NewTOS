WHAT / WHY
  TOOL07 stage 1 (measurements/measurement-2026-10-28-tool07/RUNINFO.TXT) left BIOS-STOR-002,
  -004, -005, -006 without a tosdiff case: they need boot sectors that differ from the image,
  and after a failed Getbpb EmuTOS refuses every logical access (recsiz 0, bios/blkdev.c:443-444,
  :601), so no logical restore exists. User decisions 2026-10-28 (TASK/TOOL07.md, "Entscheidungen
  des Anwenders 2026-10-28 (Rest)"): variant B -- one closing table per destructive sequence,
  marked "!disk 2 destructive", run only on a fresh disk clone on both sides, a "+set" prelude
  for the patch (format chosen by the lead), the end states of both sides compared; BIOS-STOR-002
  by a unit token resolved from the profile (oracle 18, NewTOS 26), no search; the disk canary to
  the non-destructive bios-r2.tsv once its reference reproduces twice. Deviations are findings.

DESIGN NOTE -- where the unit comes from
  A first version compiled the unit into the dumper (-DTD_DISK_UNIT=18 in the m68k build, 26 in the
  NewTOS build); it was replaced before any kept run: docs/TOS-REFERENCE-DUMPER.md section 2.1
  allows the byte order as the ONLY asymmetry between the two builds, and the decision says the
  token is resolved from the PROFILE. Now the profile's runner names the unit in D:\DISKUNIT.TXT
  (tools/hatari-oracle.sh profile disk: 18; cargo xtask tosdump --disk: 26) and DUMPBIOS reads it
  for a u:0 table only. Trial runs of the first version (scratch, not kept) gave the same oracle
  BINs byte for byte and the same NewTOS verdicts.
