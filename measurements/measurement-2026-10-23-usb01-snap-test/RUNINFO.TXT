     on base: 0 failures. VDI code is not touched by the commits; probably a shared-state race between parallel tests. Log of the failing run:
     checks/cargo-test-xtask-head-run1-flake.log. Treat as open until it shows again.
  2. Image growth: rpi4 kernel8.img 1351376 -> 1617616 bytes (+266240), qemu-virt dev 1470232 -> 1744664; llvm-size release: .data 245456 -> 470736
     (+225 KB), .bss unchanged 3567232. The snapshot store lands in .data (initialised statics), not .bss, so it is stored in the image. Harmless
     functionally (kernel end moves 0x301000 -> 0x342000, all later addresses in serial logs shift); an uninitialised/zero store would not
     enlarge the file. Dev decision.
  3. A hub's DEVICE answer (role 4) has only sections 1, 5, 6 (strings SKIPPED, no config descriptor, no interface table), entry flags 0x09 (config
     bit 1 not set) although the hub is configured. §2.5 allows missing sections; if USBSNAP should show hub details, this is where they are missing.
  4. In the first qemu probe run after the crash the shell waits for a key ("*** Press any key to continue ***") -- as with any EL0 fault.
  5. MUTE's effect on the pointer / click delivery was NOT observed (T6 needs the K10 program USBSNAP on the desktop; the probes own the screen).

REAL-PI TEST (analysis only, nothing here was run on silicon) -- for the user's later test
  a) TRB length = max packet: ROCCAT 1e7d:2cee boot mouse is ep 0x81 max 64 interval 1 (con04-pi start1-MAUS1.LOG): head arms a 64-byte TRB (base 8).
     The boot report is short (4..8 bytes) so each transfer ends as a Short Packet with IOC, the same mechanism as every mouse on silicon today
     (4-byte report in an 8-byte TRB). QEMU shows cc 13 and correct lengths (tablet len 6, mouse len 4). On silicon open: that the VL805 reports
     the short packet the same way for 64, and that the 8..64 clamp does not break the Apple keyboard (ep 0x81 max 8, ep 0x82 max 4).
     Watch in USBDIAG.LOG / serial: "transfer ... code" lines, mouse still moving, keyboard typing.
  b) EP0 ring: each device ring is 16 TRBs (CMD_RING_LEN). Head adds up to four control TDs of 3 TRBs after SET_CONFIGURATION (report descriptor,
     language list, manufacturer, product), so the EP0 ring now wraps through its Link TRB (Toggle Cycle) on every configured device [S: from code,
     counts not instrumented]. QEMU follows Link TRBs; the VL805 following the Link TRB was already an open item in the previous tester run (command
     ring). If a real device shows "transfer timeout: slot N ep 1" after the report descriptor lines, this is the first suspect.
  c) Report descriptor / strings on real devices: Apple keyboard 05ac:020c (full speed, maxpkt0 8, behind the Apple hub 05ac:1003, bcdUSB 0110 =
     transaction-translator path) and the ROCCAT. fetch_extras runs LAST and ends at the first failed EP0 transfer (STALL halts EP0, no Reset
     Endpoint); the interrupt endpoints are already armed, so a refusing device loses only its snapshot sections (SKIPPED/FAILED), not input. A
     device that never answers costs one 50M-iteration poll loop (seconds) per device at boot. Expected in the snapshot: FAILED/SKIPPED sections
     are legitimate; keyboard/mouse must still work. Compare the new boot lines "[usb] slot N iface I: report descriptor N bytes (declared M)" and
     the summary "N devices (K keyboard/mouse, O observed only), C commands issued" with the base run's "13 commands issued" on the same cabling.
  d) Observation path on silicon: ROCCAT's second interface (ep 0x82, max 64) and any report-only device are now configured instead of skipped
     (more Configure Endpoint commands than the 13 of start1/start2). Check the command count and that the mouse still moves with both plugged.
  e) Not testable in QEMU at all: cache coherence of the new DMA buffers (dcache_inval on intbuf and the report/string page), HDMI, hotplug.
