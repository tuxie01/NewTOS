  FINDINGS (not fixed; the tables measure them):
  F1 d_fname past the NUL (fs22 cases 33, 37, 39, 44, 46, 47: slots 12-13; paths cases 45, 47-52, 56,
     58-60): NewTOS writes all 14 bytes of d_fname, zero-filled after the name (makbuf,
     tos-api/src/bdos/fs/find.rs:462@makbuf); EmuTOS's packit writes the name and its NUL and leaves the
     rest of the 14 bytes as they were (bdos/fsdir.c:1297-1324, makbuf :1851-1862) -- the poison before a
     Fsfirst, a longer earlier name's tail before an Fsnext ("PXPROBE.PRG" then "DELME.TXT" leaves
     "...E.TXT" bytes behind the NUL). Visible to a program that reads d_fname past its NUL.
  F2 Dsetpath after a media change (paths case 67, S04): EmuTOS Mediach(2) = 2 after Dsetpath(C:\SUB) --
     its Dsetpath did not meet the change (the folder had been listed in part L just before); NewTOS 0 --
     its Dsetpath met the change and logged C: in again. Every other call of the table agrees, including
     G03/G04 (Dgetpath after a change: neither meets it) and D04-D08 (Dsetdrv/Dgetdrv: neither meets it).
  F3 end state of paths: the oracle's partition after the run still has C:\DELME.TXT's directory entry
     un-erased while its cluster is freed in both FATs (fsck_msdos -n exit 206, runs/fsck-ends.txt);
     NewTOS erased the entry (0xE5) and is fsck-clean. EmuTOS's ixdel writes the erase marker through the
     directory's OFD (bdos/fsopnclo.c:685-692); the sector is evidently still a dirty buffer when Hatari is
     stopped (2 s after the dumper's final LOG, tools/hatari-oracle.sh), in both oracle runs alike.
     Whether that is EmuTOS's write-back policy (a contract question) or only the capture point of the
     oracle's end state is open -- routed to the lead, not judged here.
  Retclasses that are not EXACT (Getbpb PTR_RAM, Fgetdta PTR_RAM, Fsetdta IGNORE: EmuTOS returns d0 as
  xsetdta's void left it) differ in value as expected and pass on both sides.
  fsck_msdos -n of the end states (runs/fsck-ends.txt): fs20 206 on both (the changed geometry), fs22 0 on
  both, paths 206 on the oracle (F3) and 0 on NewTOS.

WHAT STAYED PROBE-ONLY (and why; docs/TOS-REFERENCE-DUMPER.md section 6)
  - pxprobe P07 "the DTA unchanged across the Pexec, all 44 bytes": the 21 reserved bytes are each
    system's own and are not captured (x21); the identity Fgetdta() == &dta is an address. The table
    records the public fields after the Pexec (P05, d:dta) and behind Fgetdta's pointer (P07, r:dta).
  - gcprobe's text marker: the table writes buffer 0 as the poison left it (DE AD ...); where it lands is
    the end-state comparison.
  - the input traces (gcprobe-trace-check.py, pxprobe-trace-check.py): tools/biostrace-check.py reads
    neither +set nor string arguments, and GEMDOS calls are not traced.
  - the accessory loader and the AUTO folder: they run at boot; no user program reaches them after a
    media change, so there is no case. The AES shell's own Dsetpath/Dgetpath/Dsetdrv/Fdelete (dos_call)
    are kernel calls; the table measures the same GEMDOS calls from a program.
