FINDING (not a failure of any run, a gap between the argument and the code)
  TASK/V55.md and kernel/src/vbl.rs say vb_draw from the timer IRQ "interrupts no kernel code" because it runs only over EL0, and that the
  path is "the one of INPUT01/V59". vbl::irq_tick checks only `spsr_is_el0 && mode == Irq`. INPUT01's own pump (host_env::irq_input_pump ->
  input_gate::irq_pump_allowed) additionally requires a running process, upcall_depth == 0 and !aes_suspended, with the stated reason that
  an EL0 upcall (kbdvec hook, G_USERDEF callout inside an AES draw, wheel vector) runs while a kernel operation is suspended underneath it.
  irq_tick does not make that check, so vb_draw can run in an IRQ over such an upcall, i.e. between the start and the end of a suspended AES
  call (mid objc_draw). The VDI guards keep it off while HIDE_CNT or MOUSE_FLAG is set, and no backend lock exists (kernel/src/vdi_backend.rs
  has atomics only), so a hang is not to be expected; the open question is whether the pointer is hidden while a G_USERDEF callout runs
  (EmuTOS' VBL has the same exposure; NewTOS' INPUT01 deliberately excluded the case). Not driven: no G_USERDEF app was run, nothing in the
  harness exercises it. Routed to the lead/developer: either gate irq_tick with the same context as irq_pump_allowed, or correct the argument.
