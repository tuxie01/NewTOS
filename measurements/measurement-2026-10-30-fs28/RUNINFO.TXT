WHAT / WHY
  TASK/FS24 finding N1 (measurements/measurement-2026-10-29-fs24/RUNINFO.TXT): after a media change,
  Dsetpath(C:\SUB) meets the change, C: is logged in again, the call restarts and returns E_OK, but
  the next Dgetpath answers "" (the root); the oracle answers "\SUB" (gemdos-mc-fs24 cases 87, 118,
  150).

CAUSE (proven by host test against HEAD, see HOST TESTS)
  set_curdir (tos-api/src/bdos/fs/curdir.rs:229@set_curdir, HEAD :225) took the slot for the new
  path first (incr: the first free slot) and only then judged the PD's old byte with live(). After a
  re-login free_drive (tos-api/src/bdos/fs/curdir.rs:335@free_drive) has emptied the slot the byte
  names but left the byte; incr hands out that same index again, live(old) is now true, decr frees
  the slot just taken, and curdir() reads the byte as the root. The same holds for any stale byte
  (not only after a restart): the HEAD run of the fs20 test binary also failed the existing test
  current_directories_on_the_changed_drive_become_the_root once a new test had left a stale byte.
  EmuTOS xchdir reads olddir before findit (references/emutos/bdos/fsdir.c:1129, :1134); findit's
  ckdrv repairs a byte whose slot has no DND to a root slot, the first free one
  (references/emutos/bdos/fsdrive.c:121-130, references/emutos/bdos/fsdir.c:1176-1179), so the final
  decr_curdir_usage(olddir) hits that root slot, not the new directory's.

CHANGE
  set_curdir reads the old byte and judges it live BEFORE incr; a stale byte is the root (NewTOS gives
  the root no slot) and drops nothing. Order otherwise as xchdir: take the new use, store, drop the old.
  Tree: ec9e260f plus the uncommitted FS28 change:
