RUNS (attempts at reproduction: three classes; A-C are one attempt class "injector, raspi4b",
      then E-F "real USB path, virt"; D and cal were set-up / calibration)
  cal/cal2  calibration of the pointer geometry (screen 640x480, "File" at x 72-104, items 16 px).
            Their screendumps were scratch only (not kept).
  A  raspi4b, 640x480. Hover File -> New folder, leave right, re-enter, ONE click (press 100 ms).
     Result: highlight follows, leaves, returns; the one click opens "Name of new folder:"
     (screendumps/runA-24.png, runA-20.png hover state).
  B  raspi4b, same phases 3 s apart, 26 screendumps (runB-17..42). Result: leaving the box removes
     the item highlight, re-entering sets it, leaving below/right keeps the box open
     (EmuTOS OUTSIDE_STATE); NO stuck black highlight.
  C  raspi4b. Onto "New folder", then press+release delivered in ONE injector step (same tick)
     3 times (+1600/+2200/+2800), then one press-100ms-release (+3400/+3420).
     serial/runC.log: "feed 0xfa ... 0xf8" all at hz_200 4688 (+1600). Result: the three same-tick
     clicks do NOTHING, the menu stays open (screendumps/runC-30.png ... runC-32.png); the fourth,
     normal click opens the dialog (runC-33.png).
     INTERPRETATION: shows that menu::track samples buttons per pump pass and loses a press+release
     that falls into one pass (EmuTOS: event-driven). It is NOT shown that real USB reports can do
     this: usb::poll decodes ONE report per pass (see analysis section 4).
  D  virt: boot + move pointer (set-up; coordinates scaled for 1920x1080). qD-*.png.
  E  virt, REAL USB path (QMP input-send-event -> usb-mouse -> usb::poll -> hid -> ikbd::feed),
     1920x1080 16 bpp. Without a window only "Execute EmuCON" is enabled. Click with hold times
     10/20/40/80/150 ms, 3 s apart. Result: the FIRST click (10 ms) already executes EmuCON
     (screendumps/qE-click0-hold10ms.png); the later ones land in EmuCON/desktop. Clicks NOT lost.
  F  virt, real USB path: hover item, leave right/below/left, re-enter. Result: highlight follows;
     no stuck highlight (screendumps/qF-*.png).
  REPRODUCED: no, on the path that matches the real Pi. Only artificially (C, two reports in one pass).
  CAVEATS: QEMU has no Pi timing, no SD (virt), usb-mouse report cadence is QEMU's, not a 1 kHz
  receiver's; 5 ms injector grid. "New folder" itself (Dcreate) was not clicked through to the end.
