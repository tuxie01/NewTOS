 Vector 34 MEASURED: Setexc(34,h) stores the low 32 bits in the shared cell and in every page 0 ($88 reads h), logs "[hook] warning ... NewTOS never calls it" once per process, returns the old value (JUST_RTS stub 0x7e040). After VDI (115), vq_gdos (-2) and AES (200): handler called 0 times. After Ptermres the value stays, a sibling reads it; the resident code is still not called by any trap. As ADR-031 says (table row "trap and CPU vectors via Setexc"); tos-api/src/bios/vectors.rs:118@setexc.
   Trap answers: -2 returns -2, so XGDOS's own test main.c:154 would pass; -1 returns 0.
 Ptermres MEASURED: a resident program keeps text, data, bss, its Malloc block and its Mxalloc(global) block; Pexec returns 0.
 Rights per process MEASURED, all three modes (default, memprot=strict, memprot=off): a later sibling and the parent read and write the resident program's data, its Malloc block and its global block, and EXECUTE its code, no fault (VECCLI.LOG "called TSR code ... 0x1234"). Rule READ: resident private memory becomes PROT_G (tos-api/src/bdos/process/memprot.rs:47@PROT_G). Both ways rely on this.
   NOT measured: a block XGDOS allocates AFTER it is resident, while running in a caller's process: it belongs to that caller (READ). Upstream avoids that by carving everything from its TPA (main.c:160-188); xos_alloc for the memory device is meant that way.
 Cookie jar MEASURED: Ssystem(S_SETCOOKIE) 0, visible to siblings through S_GETCOOKIE. 'MiNT' and 'XGDS' absent. A direct $5A0 write as in main.c:75 only reaches the writer's page 0 (READ).
 Super/Supexec MEASURED: Supexec works and reads OSHEADER and os_run. It runs at EL0; super state grants page-0 write and nothing else (docs/api/_super-state.md S2, READ). XGDOS uses Supexec only for page-0 access and no Super (READ). No privilege is missing.
 Line-A READ: not used by XGDOS (soft.c:6, sysfont.h:6 say so; only a stale comment at soft.h:58). NewTOS has none (docs/COMPATIBILITY.md "No Line-A"). No gap.
 MiNT calls MEASURED: Syield -32, Pgetpid -32, Pkill -32. XGDOS calls them only behind the 'MiNT' cookie (xos_tos.c:84-86, READ), so they do not run, and lock.c then has no yield. Whether NewTOS can switch process inside a GEMDOS file call while XGDOS holds its lock: not measured. If yes, a contended lock spins for ever.

 The two ways of the ticket, no decision here:
  A  Kernel forwards VDI (x0=115) and vq_gdos (x0=-2) to a registered EL0 handler.
     + catches every svc #2 caller without relink: also Rust NEWDESK (programs/newtos-gem/src/vdi.rs), later an m68k thunk.
     + same trap contract as TOS: a real vector 34 in spirit.
     - kernel code and a new contract: registration, an upcall from the GEM arm (kernel/src/arch/aarch64/exceptions.rs:564@GEM_SEL_ADDR_QUERY region; deliver_upcall exists for G_USERDEF, kbdvec, Supexec), return path, a pass-through that does not recurse, Pterm during the handler, selftests; ADR-031 table amendment.
     - per VDI call while XGDOS is resident: an upcall and back, see costs. Rust NEWDESK would run through XGDOS too. The AES' own text does not: it calls the VDI inside the kernel.
  B  gemlib overlay: vdi(), vq_gdos, vq_vgdos ask a cached cookie 'XGDS' and call the resident entry directly.
     + no kernel change, vq_gdos stays -2 for everybody else, a plain function call, NEWDESK and AES untouched. The rights already suffice (measured above).
     - only relinked gemlib programs (needed anyway since V33 for vst_load_fonts). Direct svc #2 callers and later m68k programs stay without GDOS.
     - gemlib stub calls GPL-2.0-only code through a pointer: see Q6.
  Both run XGDOS in the caller's process at EL0: GEMDOS handles, Malloc owners and faults are the caller's. A fault in XGDOS ends the caller, not the system. Both turn on `_FSM` for QED, cflib, TeraDesk, HighWire at once (ticket); MODE = NOGDOS in ASSIGN.SYS (main.c:211) is the way to stage that.
  Call costs, QEMU TCG, 200 Hz clock, one boot each (ticks of 5 ms; on/strict/off), no Pi figures; TCG overstates TLB work:
    20000 Supexec(noop)           303/306/294 = 73-77 us each. Stand-in for way A's upcall; also switches the super-state page-0 rights, so upper bound.
    200000 VDI vqt_attributes     131/131/114 = 2.9-3.3 us each
    200000 Sversion               70/73/56 = 1.4-1.8 us each
  ESTIMATE, not measured: txbench on way A without GDOS. One load and branch in the GEM arm per VDI call. txbench v_gtext costs 113-116 ticks per 2000 calls (measurements/measurement-2026-11-06-v33-test/RUNINFO.TXT item 8), about 290 us per call in QEMU; the added instructions stay under 0.1 us even in TCG, so under 0.05 %, far below the tick and the host noise (113..170). Should not be measurable; to be shown by txbench before and after. Way B without GDOS: no kernel change, so nothing to measure in the kernel; gemlib gains one branch per VDI call.
