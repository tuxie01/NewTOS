WHAT / WHY
  The auditor role asks for an input check on both sides ("inputs before outputs",
  .claude/agents/auditor.md). For BIOS/XBIOS it was impossible on NewTOS: svc-seq-trace records
  function and result only, gemdos-trace GEMDOS only (docs/audits/2026-10-28-bios-storage.md
  section 11 point 4, docs/audits/2026-10-28-bios-core.md section 11 point 3). On the oracle,
  Hatari's --trace bios shows Rwabs without its sixth argument. This run adds a kernel feature
  that prints every completed trap #13/#14 call with its arguments at the width of the EmuTOS
  call form, a checker against the case table, runs bios-r1, bios-core-r1 and bios-r2 with it
  on QEMU raspi4b, proves the default build unchanged, and measures how the oracle can show
  Rwabs' sixth argument.

THE RECORD (docs/TOS-REFERENCE-DUMPER.md section 6, "Input check on NewTOS"; module doc)
  One serial-console line per completed trap #13/#14 call, written after the dispatch from the
  TrapArgs built before it:
    [biostrace] <seq:06> <caller> <trap>:0x<fn:02x>[=0x<x8>] <name> <args|-> -> 0x<x0:016x>
  caller U<slot> (EL0 process slot, U? none) or K (svc from EL1); name from the EmuTOS table,
  (empty) for an xbios_unimpl slot, (beyond) past the table; each argument x0, x1, ... at the
  width of the EmuTOS call form, read off the debug wrappers bios_N / xbios_N that sit in the same
  table slots (references/emutos bios/bios.c:895-1235, bios/xbios.c:49-1236 at 1a7484ab):
  w:0x%04x WORD/UWORD, l:0x%08x LONG/ULONG, p:0x%016x pointer; "=0x<register>" after a w:/l:
  value when the register is not the sign extension of it (same for x8). EL0 Supexec: recorded
  before the upcall, "-> upcall". To the console, not a file: no drive is written (the disk
  round compares C: byte for byte), no flush point, no buffer bound.
  Enable: cargo xtask build --board rpi4 --release --features bios-arg-trace; QEMU raspi4b with
  -append serial=on -serial file:<log>.

  One bios-r2 run on the oracle's disk profile through method/oracle-traced.sh = a copy of
  tools/hatari-oracle.sh with two additions (diff in its header comment): Hatari's
  --trace bios,xbios and a debugger script (--parse) with
      b pc = $e01050 :trace :quiet :file <out>/hd-dbg/rwabs-args.ini     rwabs-args.ini: m "a7"-"a7+20"
  $e01050 = _lrwabs in references/emutos-oracle/1a7484ab/emutos.map; the pinned ROM and the
  rebuilt etos512de.img hold the same code there (both sha256 323c87bb...d2750c).
  Measured:
  - Hatari's own trace (runs/oracle-r2/rwabs-in-hatari-trace.txt) prints five arguments:
      "BIOS 0x04 Rwabs(0,0x1037d28,1,65535,2) at PC 0x10167C0" -- lrecno is missing, as the
      audits said; first/recno = 65535 tells only that the long form was used.
  - The breakpoint dumps the argument block at lrwabs' entry (return address 0x00e00d50 =
    the trap dispatcher, then r_w, adr, numb, first, drive, lfirst), e.g. for table line 63
    "00 e0 0d 50 | 00 00 | 01 03 7d 28 | 00 01 | ff ff | 00 02 | 00 01 ff a0".
    method/oracle-rwabs-check.py: PASS, 34 lrwabs entries after "running 51 cases" = the
    table's 34 Rwabs calls (31 cases + 3 preludes) in order, 6 arguments each, 0 differ
    (runs/oracle-r2/oracle-rwabs-check.txt).
  - This run's BIN records equal tosdump/reference/EMUTOS-1a7484ab-BIOS-r2-disk.BIN (bytes 33..);
    the header differs only in the build id (3d74 vs b81d) -- the probe speaks for the reference.
    Test image unchanged (disk.sha256 before = after = d95a60c3...).
  Proposal (not done; tools/hatari-oracle.sh is unchanged): an opt-in trace mode in
  tools/hatari-oracle.sh -- --trace bios,xbios into <out>/trace.txt plus, for disk tables, the
  _lrwabs breakpoint above (address taken from the oracle build's emutos.map, not hard-coded) --

LIMITS
  - The checker ties the table to one caller by its call sequence; the dumper's own console
    lines are not used as markers (stdout buffering would not order them).
  - Supexec from EL0 is recorded before the upcall, so its value is not in the trace; a Super
    token argument (t:0, super-r1.tsv) is reported UNCHECKED. Neither occurs in the three tables.
  - QEMU raspi4b only; the instrument is UART output and needs serial=on on any board.
