## 0. Ergebnis in vier Sätzen

1. **Nicht nachgestellt** auf dem Weg, der der echten Pi entspricht (echte USB-Maus durch
   `usb::poll` → `hid` → `ikbd::feed`, QEMU `virt`, 1920×1080, 16 bpp): jeder Klick, auch der
   kürzeste (10 ms), wirkte beim ersten Mal; Hover, Verlassen und Wiedereintreten des Menüs
   hinterlassen keine stehende Markierung (Läufe E, F).
2. **Nachgestellt nur künstlich:** Wenn Drücken und Loslassen der linken Taste im selben

   das Menü bleibt offen, drei Mal hintereinander; der vierte, normal lange Klick wirkt (Lauf C).
   Das ist eine echte Abweichung von EmuTOS (Abschnitt 2, D1), aber auf der USB-Strecke gibt es
   nach dem Code keinen Weg, der zwei Berichte in einem Durchgang entschlüsselt (Abschnitt 4) —
   **Ursache für Ragnars Bild ist damit nicht bewiesen.**
3. **Kern von 19ff79f6 gegenüber HEAD:** Der Menü-Verfolger (`menu::track`), die Menü-Abfangstelle
   (`menu_intercept`) und die USB-Strecke (`kernel/src/drivers/usb/`) sind seit `19ff79f6`
   **unverändert** (`git diff --stat`, Abschnitt 3); der Fehler, falls echt, steckt also noch im
   heutigen Stand.
4. **Welches Programm:** `^N` = „New folder“ steht im Menü des eingebauten NewTOS-Desktops
   (`programs/desktop/`, EmuDESK); TeraDesks Menü hat für „New…“ in der ausgelieferten

## 2. Menü-Verfolgung gegen EmuTOS: jede Abweichung

EmuTOS: Die Steuerung läuft als eigener Prozess `ctlmgr` (`references/emutos/aes/gemctrl.c:427`),
der auf `MU_M1` über der Leiste wartet (`:456-460`) und dann `hctl_rect` → `mn_do`
(`references/emutos/aes/gemmnlib.c:249`) fährt. `mn_do` ist eine **Ereignis**-Schleife: je Zustand
ein `ev_multi` mit Mausrechtecken und Tastenwunsch (`:286-356`), Taste → `:369-376`.

NewTOS: Die Steuerung läuft **inline** im `evnt_multi` des wartenden Programms
(`tos-api/src/aes/event.rs:626@ctl_may_run`), und `menu::track_owned`
(`tos-api/src/aes/menu.rs:479@fn track_owned`) ist eine **Abfrage**-Schleife: je Durchgang Maus
und Taste lesen, Zustand vergleichen, `pump_input` (`tos-api/src/aes/menu.rs:742@pump_input`).

Rang = wie gut die Abweichung das Beschwerdebild erklären könnte (1 = am ehesten). Es ist ein
Rang der *Plausibilität*, kein Beleg.

## 4. Eingabeseite: kann die Strecke das Bild erzeugen?

Strecke **[Quelle]**: xHCI-Ereignis → `usb::poll` (`kernel/src/drivers/usb/mod.rs:201@poll_interrupt`,
**ein** Bericht je Aufruf) → `hid::mouse_report`
(`kernel/src/drivers/usb/hid.rs:66@mouse_report`; die Tasten sind das ODER aller Maus-Funktionen,
`hid_decode::combined_buttons`) → `ikbd::feed` (`kernel/src/ikbd.rs:90@feed`) →
`vdi::feed_relative` (`tos-api/src/vdi/mouse.rs:190@feed_relative`): `user_but` bei Wechsel der
unteren zwei Tastenbits (`mouse.rs:211@user_but`) = AES `button`; Position und `MOUSE_BT` per
`set_state`.

* Der Pump holt je Durchgang **einen** Bericht (`kernel/src/host_env.rs:504@pump_devices`:
  `release_held()` *oder* `usb::poll()`). Der Verfolger fragt Zustand je Durchgang — **zwischen
  zwei Berichten gibt es immer eine Abfrage.** Nach dem Code kann die Abtastung D1 also eine
  Flanke nur verlieren, wenn zwei Berichte in einem Durchgang entschlüsselt werden. Das tut nur
  der Injektor (mehrere Bytes je Tick, `tools/inject-arm.py`, Schritt in `host_env.rs`), nicht
  die USB-Strecke. **Folge:** Lauf C zeigt die Empfindlichkeit des Verfolgers, nicht ihre
  Auslösung auf der Pi.
* INPUT01 (D4): Tastenberichte halten bis zum nächsten Trap-seitigen Pump. Im Verfolger selbst
  läuft jeder Durchgang im Trap, es wird nicht gehalten. Außerhalb (Programm in EL0) wird nur
  Bewegung entschlüsselt.
* **Ungeprüft:** Berichtsrate und Durchgangsdauer auf der Pi (1080p, Cache-Pflege je Zeigerzeichnung).
  Ragnars Empfänger (Unifying, Rii X8, Cherry DW 9000; Boot-Tastatur Interface 0 + Boot-Maus
  Interface 1) und die Kabelmaus B100 (3 Byte, low speed) laufen laut seinen Aufnahmen ohne
  verlorene Berichte (`measurements/measurement-2026-10-25-usb01-ragnar2/RUNINFO.TXT`,
  „lost 0, interrupt transfer errors 0“). **[Hypothese]** (nicht belegt): mehrere Maus-Funktionen
  eines Empfängers, deren eine eine Taste „hält“ — das ODER in `combined_buttons` würde dann ein
  Loslassen verschlucken; passt zu D3 (Menü stumm bis zum nächsten sauberen Klick). Die
  USBSNAP-Aufnahmen auf eine zweite Maus-Funktion mit stehender Taste durchzusehen wäre ein
  erster Schritt (nicht getan: außerhalb des Auftrags, Umfang).

## 7. Folgerung für einen Fix (nur Vorschlag, nicht umgesetzt, bleibt Hypothese)

Erst eine Beobachtung auf der Pi (Fragen 1–5 oder ein Testszenario) trennen D1/D2/D3/Eingabe.
Die einzige belegte Abweichung ist D1; sie ließe sich ohne Annahme über die Pi schließen, indem der
Verfolger die Tastenflanken aus dem AES-Zustand (`input::button`, gebucht von `user_but`/`b_click`)
statt aus der Momentaufnahme `vdi::mouse_buttons()` liest — das ist die Ereignisbuchung, die
EmuTOS ohnehin hat. Das ist eine Änderung an `menu.rs` und an den Aufrufern; sie gehört dem
Developer, nicht dieser Untersuchung. Zuvor: Anwender-Entscheidung, ob D1 allein (belegte, aber
auf der Pi nicht als Auslöser gezeigte Abweichung) schon ein Fix-Ticket rechtfertigt.
